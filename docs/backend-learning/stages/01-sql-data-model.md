# Этап 1. SQL и модель данных

[Маршрут](../ROADMAP.md) · [← Этап 0](00-diagnostics.md) · [Этап 2 →](02-http-network-node.md)

**Оценка:** 30–40 часов. **Проект:** [Spendboard](../PROJECTS.md#проект-1-spendboard--расходы-на-свои-продукты).
**Нужно до начала:** учебная и тестовая БД из этапа 0.

**Результат:** база проекта Spendboard без HTTP и без ORM.

## Зачем этот этап

API, авторизация и конкурентные изменения опираются на модель данных. Ошибка модели потом
выглядит как баг отчёта: сумма в другой валюте, расход не в том месяце, проект пропал из итогов.
Цель этапа — самостоятельно писать запросы и защищать правила самой базой. Работа идёт через
psql/pgAdmin и SQL-файлы, без ORM, чтобы запрос всегда был виден целиком.

Точный DDL проекта — самостоятельная задача этапа. Ниже описаны вопросы и механизмы, а не готовая
схема.

## Что разобрать последовательно

### Таблица, строка, ключ, связи

Связи 1:N и N:M, нормализация на прикладных примерах. Один факт хранится в одном месте;
N:M выражается отдельной таблицей связи. Денормализация оправдана для снимков, которые не должны
меняться задним числом, например цены на момент покупки.

Документация: [учебник PostgreSQL](https://www.postgresql.org/docs/current/tutorial.html).

### NULL и ограничения

`NULL`, трёхзначная логика, `DEFAULT`, `NOT NULL`, `CHECK`, `UNIQUE`, FK, поведение удаления.
Где правило должно защищаться самой БД.

```sql
SELECT NULL = NULL AS eq, NULL IS NULL AS is_null, NULL IS DISTINCT FROM NULL AS differs;
```

Запрос ничего не меняет и возвращает `eq = NULL`, `is_null = true`, `differs = false`.
Сравнение с `NULL` даёт «неизвестно», поэтому условие `WHERE note <> 'x'` пропускает строки,
где `note` равно `NULL`. Отсюда следствия: `UNIQUE` по умолчанию допускает несколько `NULL`,
а `NOT NULL` и `CHECK` описывают допустимые данные надёжнее любой проверки в коде.
Для FK выбрать поведение при удалении родителя (`RESTRICT`, `CASCADE`, `SET NULL`)
по смыслу данных: архив проекта не должен уничтожать историю расходов.

Документация: [ограничения](https://www.postgresql.org/docs/current/ddl-constraints.html),
[сравнения и `IS DISTINCT FROM`](https://www.postgresql.org/docs/current/functions-comparison.html).

### Изменение и чтение данных

INSERT/UPDATE/DELETE с RETURNING; JOIN, GROUP BY, HAVING, EXISTS, подзапросы и CTE.
Один полезный пример оконной функции.

На что обратить внимание:

- `LEFT JOIN` сохраняет строки без пары, но `COUNT(*)` посчитает такую строку как 1,
  а `COUNT(column)` — как 0.
- Два независимых 1:N JOIN от одной строки перемножают строки. Агрегат по такой выборке
  завышен; лечится агрегацией до соединения, а не `DISTINCT`.
- `EXISTS` отвечает на вопрос «есть ли хотя бы одна строка» и не размножает результат.

Документация: [JOIN и табличные выражения](https://www.postgresql.org/docs/current/queries-table-expressions.html),
[агрегатные функции](https://www.postgresql.org/docs/current/functions-aggregate.html),
[подзапросы и EXISTS](https://www.postgresql.org/docs/current/functions-subquery.html),
[CTE](https://www.postgresql.org/docs/current/queries-with.html),
[оконные функции](https://www.postgresql.org/docs/current/tutorial-window.html),
[RETURNING](https://www.postgresql.org/docs/current/dml-returning.html).

### Деньги

Точная десятичная арифметика или minor units, код валюты, явное округление; безопасное
представление BIGINT/NUMERIC на границе JS.

- Для денег подходят `numeric` или целые копейки/центы; `real` и `double precision` —
  нет: двоичная дробь не хранит точно `0.1`.
- У суммы всегда есть валюта (трёхбуквенный код ISO 4217). Итоги считаются по каждой валюте.
- Драйвер `pg` по умолчанию возвращает `numeric` и `bigint` строками: значение больше
  `Number.MAX_SAFE_INTEGER` или с дробной частью потеряло бы точность. Преобразование через
  `Number(...)` возвращает эту проблему.

Документация: [числовые типы](https://www.postgresql.org/docs/current/datatype-numeric.html),
[типы в node-postgres](https://node-postgres.com/features/types).

### Дата и момент времени

`date` и `timestamptz`: календарная дата отличается от момента времени; отображение и группировка
в выбранном часовом поясе. Дата расхода — календарный факт, она не должна «переехать» на соседний
день из-за часового пояса. `timestamptz` хранит момент, а показывается в часовом поясе сессии.
Отчёт «за месяц» требует явно выбранного пояса и проверки конца месяца.

Документация: [типы даты и времени](https://www.postgresql.org/docs/current/datatype-datetime.html),
[функции даты и `AT TIME ZONE`](https://www.postgresql.org/docs/current/functions-datetime.html).

### Транзакции

BEGIN/COMMIT/ROLLBACK; атомарность нескольких изменений. После ошибки внутри транзакции
PostgreSQL отклоняет следующие команды до `ROLLBACK`: частичное применение невозможно.

Документация: [транзакции в учебнике](https://www.postgresql.org/docs/current/tutorial-transactions.html).

### Индексы и EXPLAIN

Индексы, порядок колонок составного индекса, селективность, цена индекса для записи.
Первое чтение EXPLAIN.

- Составной B-tree индекс помогает запросам по его левой части.
- PostgreSQL не создаёт индекс на ссылающейся колонке FK автоматически.
- Каждый индекс замедляет запись и занимает место.
- `EXPLAIN ANALYZE` выполняет запрос по-настоящему: для изменяющих запросов —
  внутри транзакции с `ROLLBACK`.

Документация: [индексы](https://www.postgresql.org/docs/current/indexes.html),
[составные индексы](https://www.postgresql.org/docs/current/indexes-multicolumn.html),
[EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html),
[Use The Index, Luke](https://use-the-index-luke.com/).

### Миграции, seed и фикстуры

Миграции и отдельные dev seed/тестовые фикстуры. Миграция — версионированное изменение схемы:
применяется один раз и после применения не редактируется, исправление оформляется новой миграцией.
Seed наполняет dev-БД; фикстуры создаются тестами и не зависят от seed.

Документация: [миграции Kysely](https://kysely.dev/docs/migrations) — runner из
[STACK.md](../STACK.md), миграции можно писать на чистом SQL.

## Практика на `projects`, `expenses`, `recurring_costs`

1. Спроектировать таблицы и объяснить каждый FK/UNIQUE/CHECK.
   - Ответить письменно: какие поля обязательны; что может повторяться; что происходит
     с расходами при архивировании и удалении проекта; какие суммы недопустимы;
     как хранится валюта; как следующая дата оплаты связана с периодом повторяющейся траты.
2. Написать 10–12 содержательных запросов: расходы за период, итоги по проектам и валютам,
   проекты без расходов, топ категорий, ближайшие даты продления, накопительный итог.
   Не суммировать разные валюты в одно число без явно заданного курса.
   - Перед запуском записать ожидаемый результат на тестовых данных, затем сравнить.
3. Проверить пограничные данные: пустая выборка, одинаковые даты, NULL, удаляемый проект,
   отрицательная сумма, большая сумма, разные валюты и конец месяца.
   - Собрать маленький набор данных, в котором встречается каждый случай.
4. Создать схему миграцией на пустой БД; отдельной миграцией добавить новое поле и индекс.
   Выполнить обновление БД, в которой уже есть тестовые записи.
   - Обязательное поле на таблице с данными требует значения для существующих строк:
     это и есть проверка миграции «на живой БД».
5. Сохранить запросы и ожидаемые результаты. Несколько ключевых ограничений и агрегаций
   закрепить интеграционными тестами; однотипные SELECT не превращать в десятки тестов.

## Эксперименты

1. **FK против предварительного SELECT в приложении.** Смоделировать проверку существования
   проекта перед вставкой расхода и удаление проекта между проверкой и вставкой. Без FK остаётся
   расход без проекта; с FK вставка завершается ошибкой нарушения ссылки.
2. **Ошибка на второй записи в транзакции.** Убедиться, что первая запись не сохранилась,
   и посмотреть, как ведут себя следующие команды до `ROLLBACK`.
3. **Изменение плана запроса до и после индекса.** Сгенерировать достаточно большой набор данных
   (например, через [`generate_series`](https://www.postgresql.org/docs/current/functions-srf.html)),
   сравнить `EXPLAIN ANALYZE` до и после индекса и время вставки.

## Критерии выхода

- Самостоятельно пишешь JOIN и агрегацию.
- Не устраняешь случайное размножение строк через DISTINCT без понимания причины.
- Объясняешь выбор типов и ограничения модели.

## Типичные ошибки

- Деньги в `double precision`; сумма разных валют в одном числе.
- `timestamptz` для календарной даты расхода.
- `COUNT(*)` после `LEFT JOIN` показывает 1 у проекта без расходов.
- `DISTINCT` скрывает размножение строк вместо исправления запроса.
- Нет индексов на колонках FK или индекс на каждой колонке «на всякий случай».
- Правка уже применённой миграции.

## Что записать как доказательство

Миграции с пояснением ограничений, файл запросов с ожидаемыми результатами, вывод
`EXPLAIN ANALYZE` до и после индекса, интеграционные тесты ограничений и агрегаций.

SQL остаётся регулярной практикой в последующих проектах.
