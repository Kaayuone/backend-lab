# Этап 2. HTTP, сеть и Node.js

[Маршрут](../ROADMAP.md) · [← Этап 1](01-sql-data-model.md) · [Этап 3 →](03-nestjs-api-tests.md)

**Оценка:** 18–24 часа. **Проект:** короткие лабораторные, например в `labs/`.
**Результат:** несколько коротких лабораторных работ.

**Цель:** понимать, что фреймворк делает поверх сети и runtime.

## Зачем этот этап

Во фронтенде HTTP виден со стороны клиента: `fetch` и вкладка Network. На сервере вопросы другие:
сколько запросов процесс обслуживает одновременно, что его блокирует, как ограничить время и объём
работы, чем сетевой сбой отличается от ответа 500. NestJS и Express скрывают эти детали, пока
не случится первый инцидент. Лабораторные короткие и без второго полноценного фреймворка.

## Что разобрать

### Семантика HTTP

HTTP methods, status codes, headers, cookies, body; безопасные и идемпотентные операции.

- Безопасный метод (`GET`, `HEAD`) не меняет состояние сервера.
- Идемпотентный (`PUT`, `DELETE`) при повторе приводит к тому же состоянию, что и один вызов.
  `POST` не идемпотентен: повтор после таймаута может создать вторую запись. Защита от этого —
  этап 5.
- 4xx — ошибка запроса, повтор без изменений не поможет; 5xx и 429 — повод для ограниченного
  повтора с задержкой.

Документация: [методы](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods),
[коды ответа](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status),
[идемпотентность](https://developer.mozilla.org/en-US/docs/Glossary/Idempotent),
[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) — первоисточник семантики.

### Сетевая ошибка и HTTP-ошибка

Различие сетевой ошибки и HTTP-ошибки; DNS, TCP, TLS и reverse proxy на уровне пути запроса.
`fetch` отклоняет промис только при сетевом сбое, а ответ 500 — успешно полученный ответ.
Коды `ENOTFOUND` (DNS), `ECONNREFUSED` (никто не слушает порт), `ETIMEDOUT`, `ECONNRESET`
указывают на разные участки пути. Reverse proxy возвращает 502/504, когда приложение за ним
недоступно или не успело ответить.

Документация: [High Performance Browser Networking](https://hpbn.co/).

### Время и объём

Keep-alive, ограничение размера запроса, connect/response/overall timeout. У HTTP-сервера Node.js
есть отдельные настройки для заголовков, всего запроса и keep-alive соединений. Клиенту нужен общий
дедлайн операции, а не только таймаут соединения: `AbortSignal.timeout()` отменяет `fetch` целиком.
Размер тела ограничивается до разбора JSON, иначе один запрос съедает память процесса.

Документация: [модуль http](https://nodejs.org/api/http.html),
[`AbortSignal.timeout()`](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static),
[`fetch` в Node.js](https://nodejs.org/api/globals.html).

### Контракт API

REST-ресурсы, пагинация и стабильная сортировка; контракт ошибок; совместимость API.
Сортировка стабильна, только если среди её ключей есть уникальный (например, id), иначе строки
с равными значениями переставляются между страницами. Добавить поле в ответ — совместимое
изменение; переименовать или удалить — нет. Формат ошибок закрепляется на этапе 3.

### CORS

CORS как ограничение браузера, а не механизм авторизации. Заголовки CORS сообщают браузеру,
можно ли скрипту с другого origin прочитать ответ. `curl` и серверный код их не проверяют.
Защиту дают аутентификация, проверка прав и защита от CSRF на этапе 4.

Документация: [MDN — CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

### Event loop

Node event loop, microtasks, libuv worker pool, I/O и CPU; Promise не создаёт поток CPU.
Пока синхронный код считает, процесс не принимает и не обслуживает другие запросы, даже если
функция объявлена `async`. Ожидание сети или диска процесс не блокирует. Часть операций
(файловая система, `crypto`, `zlib`) уходит в пул потоков libuv.

Документация: [event loop и таймеры](https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick),
[не блокировать event loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop).

### Потоки и завершение процесса

Потоки и backpressure; ограниченный параллелизм, AbortSignal и завершение процесса.

- Backpressure: если запись медленнее чтения, поток должен ждать, а не копить данные в памяти.
  `stream.pipeline()` делает это и передаёт ошибки любой части цепочки.
- Ограниченный параллелизм: тысяча одновременных запросов к внешнему API — это нагрузка,
  которую вы создали сами.
- По `SIGTERM` сервер перестаёт принимать новые запросы, дожидается текущих и закрывает пул БД.

Документация: [streams](https://nodejs.org/api/stream.html),
[backpressure](https://nodejs.org/en/learn/modules/backpressuring-in-streams),
[сигналы процесса](https://nodejs.org/api/process.html).

### Сборка и окружение

ESM, сборка TS, env и зависимости только в объёме, нужном для запуска сервера.

Документация: [ESM в Node.js](https://nodejs.org/api/esm.html).

## Лабораторные

1. Сделать минимальный HTTP-сервер с двумя маршрутами через Node `http`; закончить за 2–3 часа.
   - Разобрать метод и путь, прочитать JSON-тело с ограничением размера, вернуть осмысленные
     коды ответа для неизвестного маршрута, неверного метода и невалидного JSON.
2. Отправить корректный и некорректный запрос через `curl.exe`/HTTP-клиент, увидеть сырые ответы.
   - В PowerShell вызывать именно `curl.exe`: в Windows PowerShell 5.1 `curl` — псевдоним
     `Invoke-WebRequest`. Тело удобно передавать файлом, чтобы не бороться с кавычками:

     ```powershell
     curl.exe -i http://localhost:3000/health
     curl.exe -i -X POST http://localhost:3000/items -H "Content-Type: application/json" --data-binary "@body.json"
     ```

     `-i` показывает статус и заголовки ответа, `-v` — ещё и установку соединения.
3. Сравнить CPU-цикл и ожидающий I/O запрос: во время каждого вызвать простой health endpoint.
   - Предсказать, в каком случае health ответит сразу, а в каком — только после завершения цикла.
4. Передать большой локальный файл потоком и через чтение целиком; сравнить память.
   - Снимать `process.memoryUsage().rss` до и во время передачи.
5. Вызвать управляемую заглушку внешнего API: быстрый ответ, медленный ответ, 429 и 500.
   Добавить общий дедлайн и ограничение параллельных обращений.
   - Сначала без дедлайна и лимита: запрос к медленной заглушке висит, параллельные вызовы
     растут без ограничений. Затем с ними — и сравнить поведение.

## Критерии выхода

- Объясняешь, почему `async` не спасает от блокировки CPU.
- Умеешь ограничить время и объём операции.
- По сообщению и логам различаешь ошибку приложения, БД и сети.

## Типичные ошибки

- Ожидать, что `await` освобождает процесс во время синхронного цикла.
- Ставить таймаут соединения без общего дедлайна операции и без лимита размера тела.
- Повторять `POST` после таймаута, не зная, выполнился ли первый запрос.
- Настраивать CORS как защиту API.
- Соединять потоки через `pipe` без обработки ошибок вместо `pipeline`.

## Что записать как доказательство

Код лабораторных, сырые ответы `curl.exe`, замеры задержки health и памяти, короткие выводы
по каждому наблюдению.
