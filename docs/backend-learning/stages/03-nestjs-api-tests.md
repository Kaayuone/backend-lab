# Этап 3. NestJS, API и тесты

[Маршрут](../ROADMAP.md) · [← Этап 2](02-http-network-node.md) · [Этап 4 →](04-auth-security.md)

**Оценка:** 28–36 часов. **Проект:** [Spendboard](../PROJECTS.md#проект-1-spendboard--расходы-на-свои-продукты).
**Нужно до начала:** схема и запросы этапа 1, понимание HTTP из этапа 2.

**Результат:** Spendboard локально выполняет полезные сценарии и имеет минимальный UI.

## Зачем этот этап

NestJS даёт структуру: модули, внедрение зависимостей и конвейер обработки запроса. Задача этапа —
внедрять каждый механизм под понятную потребность и сохранить проверяемость: API работает без UI,
ошибки предсказуемы, важные сценарии проверены тестами на настоящем PostgreSQL.
Не создавать общий base service для всего CRUD.

## Что разобрать

### Модули и DI

Controllers, providers и modules; внедрение зависимостей. Интерфейс TypeScript исчезает после
компиляции и не может быть токеном DI: для абстракции нужен явный токен, и тесты подменяют
провайдер по этому же токену.

Документация: [controllers](https://docs.nestjs.com/controllers),
[providers](https://docs.nestjs.com/providers), [modules](https://docs.nestjs.com/modules),
[custom providers и токены](https://docs.nestjs.com/fundamentals/custom-providers).

### Конвейер запроса

Guards, pipes, filters, interceptors и жизненный цикл запроса. Каждый механизм отвечает за свою
задачу: guard решает, пускать ли запрос; pipe проверяет и преобразует вход; interceptor оборачивает
выполнение (например, измеряет время); exception filter превращает исключение в ответ.

Документация: [жизненный цикл запроса](https://docs.nestjs.com/faq/request-lifecycle),
[pipes](https://docs.nestjs.com/pipes), [guards](https://docs.nestjs.com/guards),
[exception filters](https://docs.nestjs.com/exception-filters),
[interceptors](https://docs.nestjs.com/interceptors).

### Валидация

Типы TypeScript не существуют во время выполнения, поэтому body, query и env проверяются
отдельно. `ValidationPipe` с `whitelist` отбрасывает неописанные поля, а `forbidNonWhitelisted`
отвечает на них ошибкой. Один подход для DTO — class-validator/class-transformer (см. [STACK.md](../STACK.md)).

Документация: [валидация в Nest](https://docs.nestjs.com/techniques/validation),
[class-validator](https://github.com/typestack/class-validator).

### Kysely

Kysely строит SQL с типами из описания схемы. Эти типы описывают ожидание кода и не проверяют,
что реальная БД им соответствует: за это отвечают миграции и интеграционные тесты. Полезно
сравнить сгенерированный SQL с запросами этапа 1.

Документация: [начало работы](https://kysely.dev/docs/getting-started),
[миграции](https://kysely.dev/docs/migrations),
[транзакции](https://kysely.dev/docs/examples/transactions/simple-transaction).

### Контракт ошибок

Единый формат с кодом, сообщением и request ID. Клиент получает стабильный код, а не текст
исключения PostgreSQL. Известные ошибки БД отображаются в ответы явно: нарушение уникальности —
в конфликт, нарушение ссылки — в ошибку входа. Формат Problem Details из RFC 9457 — хороший
ориентир, но не обязательное требование.

Документация: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

### Конфигурация, логи и жизненный цикл

Конфигурация проверяется при старте: ошибка настройки должна остановить запуск, а не всплыть
на первом запросе. Логи структурированные (JSON), с redaction секретов и токенов. Health
показывает, что процесс жив, readiness — что он может обслуживать запросы, например доступна БД.
При завершении пул соединений закрывается.

Документация: [конфигурация](https://docs.nestjs.com/techniques/configuration),
[логирование](https://docs.nestjs.com/techniques/logger), [Pino](https://getpino.io/),
[nestjs-pino](https://github.com/iamolegga/nestjs-pino),
[health checks](https://docs.nestjs.com/recipes/terminus),
[lifecycle events](https://docs.nestjs.com/fundamentals/lifecycle-events).

### OpenAPI

Описание API генерируется из декораторов и служит контрактом для web и mobile. Пример ошибки
входит в контракт так же, как успешный ответ.

Документация: [OpenAPI в Nest](https://docs.nestjs.com/openapi/introduction),
[спецификация OpenAPI](https://spec.openapis.org/oas/latest.html).

### Тесты

Unit-тест проверяет нетривиальный расчёт без БД. Integration-тест работает с настоящим PostgreSQL
и проверяет запросы и ограничения. API-тест проходит через HTTP-слой. Тестовая БД задаётся явно,
setup проверяет её имя, применяет миграции и создаёт фикстуры; setup и teardown ожидаются через
`await`.

Документация: [тестирование в Nest](https://docs.nestjs.com/fundamentals/testing),
[Vitest](https://vitest.dev/guide/), [Supertest](https://github.com/ladjs/supertest).

### Контейнер

Образ собирается в несколько стадий, Compose поднимает API и PostgreSQL. Подробная настройка
выпуска — этап 8.

Документация: [multi-stage builds](https://docs.docker.com/build/building/multi-stage/),
[Compose file](https://docs.docker.com/reference/compose-file/).

## Сделать

1. Описать 5–7 сценариев и API-контракт: создание расхода, исправление, список, фильтр,
   итоги, ближайшие продления. Добавить OpenAPI и пример ошибки.
2. Разделить HTTP DTO, бизнес-операцию и доступ к БД. Осознанно решить, где нужен repository,
   а где дополнительный интерфейс только усложнит код.
3. Подключить Kysely; сравнить несколько запросов с SQL этапа 1. Типизация запроса не заменяет
   runtime-валидацию body/query/env и не проверяет сама по себе актуальность схемы БД.
4. Настроить единый формат ошибок с кодом, сообщением и request ID. Ошибки БД и stack trace
   не выдавать клиенту; внутренние подробности оставлять в защищённых логах.
5. Реализовать лимиты пагинации, whitelist сортировки, явные правила PATCH и обработки NULL.
   - Решить и записать: отсутствующее поле в PATCH означает «не менять», а `null` — «очистить»
     или ошибку, в зависимости от поля.
6. Валидировать конфигурацию при старте, добавить структурированные логи с redaction,
   health/readiness и корректное закрытие пула при завершении.
7. Сделать простой UI через AI; API должно оставаться полностью проверяемым без него.
   UI ограничен примерно 2–4 часами.
8. Собрать контейнер и поднять API + PostgreSQL через Compose локально.

## Тестовый минимум

- Unit-тест для нетривиального расчёта/преобразования.
- Integration-тест запросов и ограничений на настоящем PostgreSQL.
- API-тест успешного сценария, плохого ввода, отсутствующего объекта и пагинации.
- Отдельный `TEST_DATABASE_URL`, проверка разрешённой тестовой БД, миграции и fixtures.
  Setup/teardown должны завершаться с `await`; тесты не используют реальные личные данные.

## Эксперименты

1. **Пересоздать только одноразовую тестовую БД и запустить suite с нуля.** Если тесты зависят
   от оставшихся данных или порядка запуска, это проявится здесь.
2. **Изменить контракт ошибки и увидеть, какой тест защищает клиента.** Если ни один тест
   не упал, контракт ошибок не защищён.

## Критерии выхода

- Приложение запускается по README.
- Данные переживают перезапуск.
- Важные сценарии проверены автоматически.

Покрытие в процентах не является критерием завершения.

## Типичные ошибки

- Общий base service для CRUD всех сущностей.
- Repository-интерфейс без второй реализации и без причины.
- DTO повторяет таблицу БД и отдаёт клиенту лишние поля.
- Типы Kysely воспринимаются как проверка схемы БД.
- Клиент получает текст ошибки PostgreSQL или stack trace.
- Тесты зависят от порядка запуска или общих данных.

## Что записать как доказательство

OpenAPI-описание, README с командами запуска, тесты из тестового минимума, результат
экспериментов с пересозданной БД и изменённым контрактом ошибки.
