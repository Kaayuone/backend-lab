# Этап 5. Транзакции, гонки и идемпотентность

[Маршрут](../ROADMAP.md) · [← Этап 4](04-auth-security.md) · [Этап 6 →](06-telegram-queue-worker.md)

**Оценка:** 16–22 часа. **Проект:** [Spendboard](../PROJECTS.md#проект-1-spendboard--расходы-на-свои-продукты)
и отдельная маленькая лабораторная. **Нужно до начала:** транзакции этапа 1, API этапа 3.

**Результат:** проверенные сценарии гонок и повторов.

**Цель:** сохранять правила при параллельных запросах и повторах клиента.

## Зачем этот этап

При ручной проверке запросы приходят по одному. В реальной работе приложения открыты две вкладки,
кнопку нажимают дважды, мобильный клиент повторяет запрос после таймаута, worker обрабатывает
задачу параллельно с API. Инварианты ломаются молча: правка теряется, квота превышается, операция
выполняется дважды. Этап учит воспроизводить гонку детерминированно и выбирать самый простой
способ защиты конкретного инварианта.

Новые транзакции и правила защиты проектируются самостоятельно; ниже — механизмы, из которых
выбирать.

## Что разобрать

### Read Committed и MVCC

В PostgreSQL по умолчанию действует Read Committed: каждый запрос видит данные, зафиксированные
к его началу. Чтение не блокирует запись. Если приложение прочитало строку, изменило значение
в памяти и записало его обратно, параллельное изменение между чтением и записью теряется — это
lost update. Повторное чтение в той же транзакции может увидеть уже другие данные.

Документация: [уровни изоляции](https://www.postgresql.org/docs/current/transaction-iso.html),
[введение в MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html).

### Блокировки и deadlock

`UPDATE` блокирует изменяемую строку до конца транзакции; второй `UPDATE` той же строки ждёт.
Две транзакции, захватывающие строки в разном порядке, могут ждать друг друга: PostgreSQL
обнаруживает deadlock и отменяет одну из них. Порядок захвата строк — часть дизайна.
`lock_timeout` ограничивает ожидание блокировки, а представление `pg_locks` показывает,
кто кого ждёт.

Документация: [явные блокировки](https://www.postgresql.org/docs/current/explicit-locking.html),
[`lock_timeout`](https://www.postgresql.org/docs/current/runtime-config-client.html),
[`pg_locks`](https://www.postgresql.org/docs/current/view-pg-locks.html),
[мониторинг блокировок](https://wiki.postgresql.org/wiki/Lock_Monitoring).

### Способы защиты инварианта

Сравнить optimistic concurrency, условный UPDATE, UNIQUE и SELECT FOR UPDATE; понимать,
когда нужен более строгий уровень изоляции.

- **Optimistic concurrency.** Клиент присылает версию, которую видел; изменение применяется,
  только если версия не изменилась, иначе — конфликт. Блокировки не держатся между запросами.
- **Условный UPDATE.** Проверка инварианта входит в условие самого изменения, поэтому
  проверка и запись выполняются атомарно.
- **UNIQUE.** Уникальность гарантирует только ограничение БД; `INSERT ... ON CONFLICT`
  позволяет обработать повтор без ошибки.
- **SELECT FOR UPDATE.** Строка блокируется на время транзакции; подходит, когда решение
  требует нескольких шагов чтения и записи.
- **Repeatable Read и Serializable** защищают от большего числа аномалий, но транзакцию
  приходится повторять при ошибке сериализации.

Документация: [`FOR UPDATE`](https://www.postgresql.org/docs/current/sql-select.html),
[`ON CONFLICT`](https://www.postgresql.org/docs/current/sql-insert.html).

### Транзакции в коде приложения

Все запросы одной транзакции идут через одно соединение из пула. Запрос «мимо» транзакции
выполнится в другом соединении и не откатится вместе с ней. Транзакция не держится открытой
во время запроса к внешнему сервису: блокировки и соединение заняты всё время ожидания.

Документация: [транзакции в node-postgres](https://node-postgres.com/features/transactions),
[транзакции в Kysely](https://kysely.dev/docs/examples/transactions/simple-transaction).

### Идемпотентность

Клиент, не получивший ответ, не знает, выполнилась ли операция. Idempotency key позволяет
безопасно повторить запрос: ключ уникален в области пользователя и операции, сервер хранит
результат первого выполнения и сравнивает payload повтора с исходным. Тот же ключ с другим
payload — ошибка клиента, а не повод выполнить новую операцию.

Документация: [идемпотентные запросы Stripe](https://docs.stripe.com/api/idempotent_requests),
[черновик IETF Idempotency-Key](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/).

## Практика

1. В Spendboard добавить `version` для редактируемого расхода и конфликт при устаревшем изменении.
   Два клиента не должны молча терять правки друг друга.
2. В отдельной маленькой лабораторной дать двум запросам последнее доступное место/единицу квоты.
   Сначала воспроизвести нарушение, затем защитить инвариант транзакцией или атомарным SQL.
3. Для одной составной операции вызвать ошибку после первого изменения и доказать rollback.
4. Смоделировать повтор запроса после неизвестного результата. Реализовать idempotency key:
   область пользователя/операции, уникальность, сравнение payload и повтор результата.
5. Показать разницу между дедупликацией запроса, идемпотентной операцией и повторной отправкой
   ответа. TTL записи выбирать по договорённости, а не случайной константой.

### Как воспроизводить гонку

Гонка воспроизводится, когда обе операции гарантированно оказываются между чтением и записью
одновременно. Для этого нужны два независимых соединения и барьер: обе транзакции читают данные,
ждут общего сигнала и только потом пишут. Один удачный последовательный запуск отсутствие гонки
не доказывает.

## Эксперименты

1. **Два независимых соединения к БД и управляемый барьер запуска.** Повторить сценарий много раз
   до и после защиты, записать число нарушений.
2. **Конфликт версий.** Два клиента редактируют одну версию расхода; второй получает конфликт.
3. **Одинаковый ключ с другим payload.** Сервер отклоняет повтор и не выполняет новую операцию.
4. **Lock timeout.** Одна транзакция держит блокировку, вторая с `lock_timeout` завершается
   ошибкой вместо бесконечного ожидания.

Не доказывать отсутствие гонки одним удачным последовательным запуском.

## Критерии выхода

- Объясняешь, почему проверка SELECT перед INSERT не заменяет UNIQUE.
- Не держишь DB-транзакцию открытой во время запроса к внешнему сервису.
- Умеешь выбрать самый простой способ защиты конкретного инварианта.

## Типичные ошибки

- Проверка существования перед вставкой без ограничения в БД.
- Транзакция открыта во время HTTP-запроса к внешнему сервису.
- Части одной транзакции выполняются через разные соединения пула.
- Бесконечный повтор при deadlock или отсутствие повтора при ошибке сериализации.
- Idempotency key без сравнения payload: другой запрос с тем же ключом получает чужой результат.

## Что записать как доказательство

Тест конфликта версий, лабораторная гонки с результатами до и после защиты, тест rollback,
тесты idempotency key для повтора и для другого payload.

Читать по эксперименту: [PostgreSQL — уровни изоляции](https://www.postgresql.org/docs/current/transaction-iso.html).
