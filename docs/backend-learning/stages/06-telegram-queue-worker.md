# Этап 6. Telegram-бот, очередь и worker

[Маршрут](../ROADMAP.md) · [← Этап 5](05-transactions-concurrency.md) · [Этап 7 →](07-files-integrations.md)

**Оценка:** 32–44 часа. **Проект:** [Audio Bot](../PROJECTS.md#проект-2-audio-bot--личный-telegram-бот-для-аудио).
**Нужно до начала:** потоки и процессы этапа 2, транзакции и идемпотентность этапа 5.

**Результат:** Audio Bot из задания проекта, работающий для личного использования.

## Зачем этот этап

Скачивание и конвертация занимают минуты, а обработчик сообщения должен отвечать сразу. Telegram
повторяет доставку update, пользователь отправляет ссылку повторно, процесс перезапускается
посреди работы. Нужны быстрый приём задачи, состояние задания в БД, очередь с ограниченными
повторами, worker с лимитами ресурсов, уборка временных файлов и честная семантика доставки.

Лимиты, состояния и требования к боту описаны в [PROJECTS.md](../PROJECTS.md); здесь — порядок
изучения и механизмы.

## Что разобрать

### Updates в Telegram

Бот получает update через polling (`getUpdates`) или webhook. У каждого update есть
`update_id`; неподтверждённые updates доставляются повторно, поэтому обработчик должен быть
идемпотентным. Webhook защищается секретным токеном, который Telegram передаёт в заголовке.
Начать с polling; два способа одновременно не поддерживать.

Документация: [получение updates](https://core.telegram.org/bots/api#getting-updates),
[`setWebhook`](https://core.telegram.org/bots/api#setwebhook),
[FAQ ботов](https://core.telegram.org/bots/faq), [grammY](https://grammy.dev/guide/),
[polling или webhook в grammY](https://grammy.dev/guide/deployment-types),
[повторы при 429 в grammY](https://grammy.dev/plugins/auto-retry).

### Очередь BullMQ

Очередь хранит задачи в Redis, worker забирает их с заданной конкурентностью. Попытки
с задержкой (backoff) и конечным числом повторов задаются при добавлении задачи. Задача с тем же
`jobId` не добавляется повторно, пока существует предыдущая. Если worker умер, блокировка задачи
истекает, и она считается зависшей (stalled) и возвращается в обработку.

Документация: [BullMQ](https://docs.bullmq.io/), [workers](https://docs.bullmq.io/guide/workers),
[concurrency](https://docs.bullmq.io/guide/workers/concurrency),
[повторы](https://docs.bullmq.io/guide/retrying-failing-jobs),
[stalled jobs](https://docs.bullmq.io/guide/workers/stalled-jobs),
[job id](https://docs.bullmq.io/guide/jobs/job-ids),
[соединения](https://docs.bullmq.io/guide/connections),
[подготовка к production](https://docs.bullmq.io/guide/going-to-production) — в том числе
политика памяти Redis `noeviction` и сохранность данных.

### Разрыв между БД и очередью

Запись задания в БД и отправка в Redis — две разные системы; процесс может упасть между ними.
Outbox решает это так: задание и намерение отправки записываются в одной транзакции БД,
отдельный dispatcher отправляет их в очередь и повторяет отправку с тем же устойчивым ID.
Брокер может доставить задачу повторно, поэтому worker идемпотентен.

Документация: [Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html),
[идемпотентные задачи BullMQ](https://docs.bullmq.io/patterns/idempotent-jobs).

### Повторы и классы ошибок

Повторять имеет смысл временные сбои: сеть, таймаут, 429, 5xx. Постоянные отказы — удалённый
ролик, неподдерживаемая ссылка, слишком большой файл — завершают задание сразу с понятной
причиной. Задержка растёт экспоненциально и со случайным разбросом (jitter), чтобы повторы
не приходили одновременно.

Документация: [Exponential backoff and jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/).

### Дочерние процессы и файлы

yt-dlp и FFmpeg запускаются через `spawn` с массивом аргументов, без shell: пользовательский
текст не превращается в команду. У процесса есть таймаут; при отмене завершается вся группа
процессов, иначе FFmpeg может продолжить работу после родителя. Дочернему процессу передаётся
минимальное окружение без токенов. Каждое задание работает в своём временном каталоге.

Документация: [child_process](https://nodejs.org/api/child_process.html),
[`fs.mkdtemp` и файловая система](https://nodejs.org/api/fs.html),
[yt-dlp](https://github.com/yt-dlp/yt-dlp), [установка yt-dlp](https://github.com/yt-dlp/yt-dlp/wiki/Installation),
[FFmpeg](https://ffmpeg.org/ffmpeg.html).

### Ресурсы и доставка

Лимиты CPU и памяти задаются контейнеру worker, конкурентность — очереди. Отправка в Telegram
может завершиться таймаутом уже после того, как Telegram принял файл: состояние доставки тогда
неизвестно, и обещать exactly-once нельзя.

Документация: [ограничения ресурсов Docker](https://docs.docker.com/engine/containers/resource_constraints/),
[`sendAudio`](https://core.telegram.org/bots/api#sendaudio).

## Порядок реализации

1. Через grammY принять ссылку только от разрешённых Telegram ID; показать статус задачи.
   Начать с polling. Для webhook изучить HTTPS и secret token, не поддерживать оба способа одновременно.
2. Сначала сделать адаптер, который возвращает маленький локальный аудиофайл.
   Это отделяет проверку приложения от нестабильности внешнего источника.
3. Вынести долгую работу в BullMQ worker. В БД хранить задание и его состояния;
   обработчик update только проверяет вход и надёжно фиксирует принятие.
4. Разобрать разрыв «записали задачу в БД, но не положили в Redis». Реализовать небольшой
   outbox/dispatcher: запись задания и намерения отправки в одной DB-транзакции, повторная
   отправка с устойчивым ID, идемпотентный worker. Брокер может доставить задачу повторно.
5. Подключить yt-dlp/FFmpeg через `spawn` с массивом аргументов и без shell.
   Для каждого задания отдельный временный каталог, фиксированные параметры и таймаут.
6. Ограничить вход, длительность, размер, число одновременных работ, диск, CPU/память
   контейнера. Отменять или завершать зависший дочерний процесс вместе с его потомками.
7. Разделить повторяемые сетевые ошибки и постоянные отказы: удалённый ресурс, неподдерживаемая
   ссылка, слишком большой файл. Показать пользователю понятный результат.
8. Отправить аудио в Telegram; записать статус доставки и удалить временные файлы.
   Очистка выполняется и после ошибки; отдельная уборка удаляет остатки после аварии процесса.
9. Для Redis очереди проверить сохранение данных и политику `noeviction`. В БД остаётся
   источник состояния задач: сверка должна находить принятые, но потерянные очередью задания
   и зависшие попытки. Восстановление Redis не заменяет идемпотентность обработки.

Для проверок использовать свои или разрешённые к скачиванию материалы.

## Эксперименты

Для каждого эксперимента заранее записать ожидаемое состояние задания в БД.

1. **Перезапуск worker посреди обработки.** Задача возвращается в работу по ограниченной
   политике, временные файлы прошлой попытки убираются.
2. **Недоступный Redis после commit.** Задание остаётся ожидающим отправки, dispatcher
   отправляет его после восстановления Redis.
3. **Два одинаковых update.** Создаётся одно задание.
4. **Повтор задачи после завершения.** Результат не перезаписывается, лишней обработки нет.
5. **Переполнение лимита.** Пользователь получает понятный отказ, очередь не растёт без границ.
6. **Таймаут при отправке результата в Telegram.** Состояние становится `delivery_unknown`,
   файл сохранён для явной повторной выдачи.

## Критерии выхода

- API и бот отвечают во время конвертации.
- Принятая задача не теряется в разрыве БД/очередь.
- Повтор не создаёт несколько вычислений без необходимости.
- После сбоя нет вечного `processing` и забытых файлов.

Не обещать exactly-once для внешней отправки: таймаут Telegram может оставить неизвестным,
доставлено ли сообщение.

## Типичные ошибки

- Скачивание и конвертация выполняются прямо в обработчике update.
- Redis считается источником состояния задач вместо БД.
- `jobId` генерируется заново при каждой отправке, и защита от дублей не работает.
- Команда собирается строкой и запускается через shell.
- Завершается только родительский процесс, а FFmpeg продолжает работу.
- Уборка файлов только в `finally`: после аварии процесса файлы остаются.
- Бесконечные повторы постоянных ошибок.
