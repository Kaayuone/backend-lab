# Этап 0. Диагностика и среда

[Маршрут](../ROADMAP.md) · [Этап 1 →](01-sql-data-model.md)

**Оценка:** 6–8 часов. **Проект:** нет, подготовка. **Результат:** карта пробелов и безопасная
учебная БД.

**Цель:** установить фактическую исходную точку и отделить учебные данные от ценных.

## Зачем этот этап

Язык и инструменты уже знакомы по фронтенду, но серверные ошибки чаще всего возникают на стыках:
сеть, пул соединений, права пользователя БД, состояние в volume. Диагностика нужна, чтобы тратить
часы на реальные пробелы, а не повторять известное. Результат — конкретный список пробелов
в [PROGRESS.md](../PROGRESS.md), а не оценка уровня: диагностика не выставляет грейд.

Вторая задача — безопасность данных. Следующие этапы будут удалять и пересоздавать записи,
поэтому учебная, тестовая и любая ценная БД должны быть разделены до первого эксперимента.

## Что разобрать

### Путь запроса

`клиент → DNS → HTTPS → сервер → пул соединений → БД → ответ`. На каждом участке можно задать
три вопроса: что будет при таймауте, что будет при отказе и где данные могут утечь. Примеры
утечек: токен в URL попадает в логи прокси, ответ API содержит лишние поля, порт БД открыт наружу.

Документация: [MDN — обзор HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview),
[High Performance Browser Networking](https://hpbn.co/) — главы о TCP, TLS и HTTP.

### Connection string и пользователь БД

Строка вида `postgres://user:password@host:port/database` описывает, куда и под кем подключается
приложение. Пользователь БД — это роль PostgreSQL, а не пользователь приложения. Приложению
достаточно прав на свою БД; работать суперпользователем `postgres` удобно, но тогда любая ошибка
или утечка строки подключения даёт полный доступ к серверу.

Документация: [строки подключения libpq](https://www.postgresql.org/docs/current/libpq-connect.html),
[роли](https://www.postgresql.org/docs/current/user-manag.html),
[аутентификация клиентов](https://www.postgresql.org/docs/current/client-authentication.html),
[psql](https://www.postgresql.org/docs/current/app-psql.html),
[pgAdmin](https://www.pgadmin.org/docs/pgadmin4/latest/index.html).

### Docker: порт, сеть и volume

- Опубликованный порт связывает порт хоста с портом контейнера. С хоста подключение идёт
  через порт хоста, из соседнего контейнера — по имени сервиса Compose и порту контейнера.
- `localhost` внутри контейнера означает сам контейнер, а не компьютер.
- Volume хранит данные отдельно от контейнера: пересоздание контейнера их не удаляет,
  а `docker compose down -v` удаляет.

Документация: [volumes](https://docs.docker.com/engine/storage/volumes/),
[сети Compose](https://docs.docker.com/compose/how-tos/networking/),
[образ postgres](https://hub.docker.com/_/postgres).

### Изоляция учебной и тестовой БД

Тестовая БД отдельная, с явной переменной `TEST_DATABASE_URL`. Если переменная не задана,
тесты должны падать, а не подключаться к рабочей БД по умолчанию. Перед очисткой данных
setup проверяет имя БД. Тогда ошибка конфигурации остаётся ошибкой запуска, а не потерей данных.

### Версии и окружение

Зафиксировать поддерживаемую LTS-версию Node.js, команды запуска и правило для `.env`:
файл с секретами не коммитится, рядом лежит `.env.example` с именами переменных. Минимальный
учебный проект проверяется форматированием, линтером и `tsc` в strict-режиме.

Документация: [релизы Node.js](https://nodejs.org/en/about/previous-releases),
[`--env-file` в CLI Node.js](https://nodejs.org/api/cli.html),
[`strict` в tsconfig](https://www.typescriptlang.org/tsconfig/#strict),
[ESLint](https://eslint.org/docs/latest/use/getting-started),
[Prettier](https://prettier.io/docs/install).

## Сделать

1. Нарисовать путь `клиент → DNS → HTTPS → сервер → пул соединений → БД → ответ`.
   Отметить, на каких участках возможны таймаут, отказ и утечка данных.
   - Для каждого участка записать одну строку: отказ, симптом у клиента и где его видно
     (ошибка клиента, лог приложения, лог БД).
2. Без AI написать SELECT с JOIN и агрегацией; объяснить FK, UNIQUE и транзакцию.
   Документацией пользоваться можно. Пробелы записать в [PROGRESS.md](../PROGRESS.md).
   - Взять две-три небольшие таблицы с данными. Места, где пришлось открыть документацию
     или ошибся первый вариант запроса, и есть список пробелов.
3. Подготовить изолированные учебную и тестовую БД, понять connection string, порт,
   Docker network и volume. Проверить подключение из приложения и pgAdmin/psql.
   - Проверочный запрос, одинаковый для приложения и pgAdmin:

     ```sql
     SELECT current_user, current_database(), inet_server_port();
     ```

     Он ничего не меняет и показывает, под каким пользователем, к какой БД и на какой порт
     сервера установлено соединение. Результаты из приложения и pgAdmin должны совпасть
     с ожидаемыми для каждой из двух БД.
4. Взять понятные части текущего Nest-кода из `old/garage-rest-api` как примеры. Не тратить этап
   на уборку всего репозитория и завершение прежних задач.
5. Зафиксировать версии runtime, команды запуска и принцип обращения с `.env`.
   Настроить форматирование, lint и проверку типов минимального учебного проекта.

## Эксперименты

1. **Остановить учебную БД и сравнить ошибку подключения с ошибкой неверного пароля.**
   Сначала предсказать оба сообщения. Остановленный сервер даёт отказ на уровне TCP
   (`ECONNREFUSED`), неверный пароль — ответ PostgreSQL об ошибке аутентификации.
   Записать, как каждая ошибка выглядит в логе приложения и в psql.
2. **Перезапустить контейнер и проверить сохранность данных в volume.** Создать запись,
   перезапустить контейнер, найти запись. Затем на учебной БД объяснить, какая команда
   удалила бы данные вместе с volume. Выполнять её только на учебной БД.

## Критерии выхода

- Объясняешь, где живут данные.
- Объясняешь, каким пользователем приложение входит в БД.
- Объясняешь, почему тесты не должны подключаться к dev/prod.

## Типичные ошибки

- Все приложения и тесты подключаются одним суперпользователем.
- Пароль хранится в коде или README, `.env` попадает в git.
- Путаются порт хоста и порт контейнера; из контейнера используется `localhost`.
- Тестовая очистка выполняется без проверки, к какой БД установлено соединение.

## Что записать как доказательство

Схема пути запроса, список пробелов SQL/HTTP, команды запуска, вывод проверочного запроса
из приложения и pgAdmin, наблюдения двух экспериментов.
