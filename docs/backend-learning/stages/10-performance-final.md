# Этап 10. Производительность и итоговая проверка

[Маршрут](../ROADMAP.md) · [← Этап 9](09-saas-payments.md)

**Оценка:** 18–26 часов. **Проект:** Feedback Inbox и при необходимости части других проектов.
**Нужно до начала:** все предыдущие этапы.

**Результат:** измерения, разбор сбоев, готовность к своему продукту.

**Цель:** понять пределы своего решения и принимать решения на основании измерений.

## Зачем этот этап

Оптимизация без измерения — догадка. Этап учит описывать нагрузку, измерять задержку
в перцентилях, находить узкое место (часто это SQL или пул соединений), исправлять его и
доказывать эффект. Результаты относятся к конкретной среде: ноутбук и сервер дадут разные
числа, и это нормально, если среда записана.

## Что разобрать

### Профиль нагрузки и метрики

Размер данных, среда, число одновременных клиентов, p50/p95 задержки, доля ошибок, throughput,
CPU/память и соединения БД. Среднее значение скрывает медленный хвост, поэтому смотреть нужно
перцентили. Перед изменением фиксируется базовое измерение.

Документация: [autocannon](https://github.com/mcollina/autocannon), [k6](https://github.com/grafana/k6).

### Медленный SQL

`EXPLAIN ANALYZE` на тестовых данных показывает фактический план и время. Расширение
`pg_stat_statements` собирает статистику по всем запросам и показывает самые затратные.
Частые причины: N+1, лишний JOIN, полное сканирование, неподходящий индекс, слишком большая
выдача.

Документация: [EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html),
[pg_stat_statements](https://www.postgresql.org/docs/current/pgstatstatements.html).

### Пагинация

Offset заставляет БД пропускать строки, а при изменении списка между запросами страницы
сдвигаются. Cursor (keyset) pagination продолжает выборку от последней показанной строки
по стабильному порядку с уникальным ключом в конце сортировки.

Документация: [пагинация без offset](https://use-the-index-luke.com/no-offset),
[построчное сравнение](https://www.postgresql.org/docs/current/functions-comparisons.html).

### Кэш

Ключ, TTL, tenant в ключе, инвалидирование и устаревший ответ. Кэш добавляет второй источник
правды: без tenant в ключе он отдаст чужие данные, без инвалидирования — старые. Кэш остаётся
только при измеренной пользе.

Документация: [MDN — HTTP-кэширование](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)
как пример модели устаревания.

### Процессы, пулы и backpressure

Общее число соединений к БД — это число процессов, умноженное на размер пула каждого.
Оно должно оставаться ниже `max_connections` с запасом для служебных подключений. Рост числа
API-процессов без пересчёта пула приводит к отказам подключения. Ограничение конкурентности
worker и отказ при переполнении лучше бесконечного накопления задач.

Документация: [пул в node-postgres](https://node-postgres.com/features/pooling),
[настройки подключений PostgreSQL](https://www.postgresql.org/docs/current/runtime-config-connection.html),
[PgBouncer](https://www.pgbouncer.org/).

### Трассировка и профилирование

Trace связывает шаги одного запроса или задачи между процессами; request ID в логах — минимальная
версия той же идеи. Большой observability-стек для этого не обязателен. Flame graph показывает,
на что уходит CPU процесса Node.js.

Документация: [введение в observability](https://opentelemetry.io/docs/concepts/observability-primer/),
[traces](https://opentelemetry.io/docs/concepts/signals/traces/),
[flame graphs в Node.js](https://nodejs.org/en/learn/diagnostics/flame-graphs).

## Сделать

1. Выбрать один пользовательский запрос и одну фоновую задачу. Зафиксировать размер данных,
   среду, профиль нагрузки, p50/p95, ошибки, throughput, CPU/память и соединения БД.
2. Найти медленный SQL через EXPLAIN ANALYZE на тестовых данных: N+1, ненужный JOIN,
   полное сканирование, неправильный индекс, слишком большая выдача.
3. Сравнить offset и cursor pagination на изменяемом списке со стабильным порядком.
4. Провести один эксперимент с кэшем: ключ, TTL, tenant, инвалидирование и устаревший ответ.
   Оставить кэш в приложении только если есть измеренная польза.
5. Показать, что увеличение числа API-процессов меняет общий размер DB-пула и лимиты.
   Backpressure/лимит worker важнее бесконечного накопления задач.
6. Прочитать метрики и логи одного сквозного запроса/задачи; понять назначение trace,
   не разворачивая обязательный большой observability-стек.
7. Пройти итоговый сценарий: новый пользователь → ресурс → фоновая работа → тестовая оплата →
   повтор уведомления → перезапуск → проверка доступа → восстановление backup.
   Если сценарий пересекает проекты, продемонстрировать соответствующие части отдельно.
8. Подготовить короткий разбор: архитектура, 3 инварианта, 3 отказа, результаты измерений,
   ограничения, следующий шаг при росте нагрузки. Защитить решения без подсказок AI.

## Критерии выхода

- Можешь показать причину проблемы и эффект исправления.
- Понимаешь, что измеренные результаты относятся к конкретной среде.
- Не называешь приложение готовым к произвольному highload.

## Типичные ошибки

- Измерения на пустой БД, перенесённые на реальные данные.
- Только средняя задержка без перцентилей.
- Кэш без tenant в ключе и без инвалидирования.
- Увеличение размера пула, пока БД не перестанет принимать подключения.
- Оптимизация без базового измерения.

## Что записать как доказательство

Протокол измерений до и после исправления с описанием среды, планы запросов, итоговый сценарий
и короткий письменный разбор.
