# Этап 4. Учётные записи и безопасность

[Маршрут](../ROADMAP.md) · [← Этап 3](03-nestjs-api-tests.md) · [Этап 5 →](05-transactions-concurrency.md)

**Оценка:** 24–32 часа. **Проект:** [Spendboard](../PROJECTS.md#проект-1-spendboard--расходы-на-свои-продукты).
**Нужно до начала:** API и тесты этапа 3.

**Результат:** приватное приложение с корректными границами доступа.

## Зачем этот этап

Authentication отвечает на вопрос «кто это», authorization — «что ему можно». В небольших
продуктах утечки чаще происходят из-за ошибок авторизации, чем из-за криптографии: чужая запись
доступна по известному ID, агрегат считает данные всех пользователей, экспорт не проверяет
владельца. Цель этапа — один раз пройти серверные сессии с отзывом, проверки владения во всех
путях доступа и понять, сколько стоит поддержка собственной auth в продукте.

Публичная регистрация, MFA и несколько социальных провайдеров не обязательны для первого проекта.

## Что разобрать

### Кто и что может

Различие authentication/authorization; идентичность пользователя, владение объектом, роль
и разрешение. Пользователь определяется по проверенной сессии, а не по `userId` из body.
Проверка прав нужна в каждом пути к данным: чтение по ID, список, изменение, агрегаты, экспорт.

Документация: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html),
[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html),
[OWASP IDOR](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html).

### Пароли

Пароли хешируются готовой библиотекой медленного хеширования (например, Argon2id), со своими
параметрами и солью внутри результата. Собственные схемы хеширования не пишутся.

Документация: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[node-argon2](https://github.com/ranisalt/node-argon2).

### Серверная сессия

Клиент получает случайный непредсказуемый токен в cookie, сервер хранит запись сессии с владельцем
и сроком действия. Хранить в БД лучше хеш токена: утечка таблицы тогда не даёт готовых сессий.
При входе выдаётся новая сессия (защита от session fixation); выход удаляет одну сессию,
«выйти везде» — все сессии пользователя.

Документация: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[аутентификация в Nest](https://docs.nestjs.com/security/authentication),
[сессии в Nest](https://docs.nestjs.com/techniques/session).

### Cookie, CSRF и прокси

- `HttpOnly` скрывает cookie от JavaScript, `Secure` запрещает отправку по HTTP, `SameSite`
  ограничивает отправку при запросах с других сайтов. Префикс `__Host-` закрепляет cookie
  за хостом.
- Cookie отправляется браузером автоматически, поэтому изменяющие запросы нужно защищать
  от CSRF: `SameSite`, проверка `Origin` и при необходимости CSRF-токен. CORS эту задачу
  не решает.
- За reverse proxy приложение видит адрес прокси. Доверять `X-Forwarded-*` можно только
  от своего прокси, иначе клиент подделает IP и протокол.

Документация: [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie),
[MDN — cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies),
[OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html),
[CSRF в Nest](https://docs.nestjs.com/security/csrf),
[Express за прокси](https://expressjs.com/en/guide/behind-proxies.html).

### Перебор и утечки через ответы и логи

Число попыток входа ограничивается. Ответ и время ответа не должны выдавать, существует ли
аккаунт. Пароли, токены сессий и ссылки восстановления не попадают в логи.

Документация: [rate limiting в Nest](https://docs.nestjs.com/security/rate-limiting),
[OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

### Восстановление доступа

Одноразовый токен с коротким сроком действия хранится как хеш и гасится после использования.
После смены пароля разумно отозвать остальные сессии. Письмо на этом этапе уходит в локальный
email sink; настоящий транспорт подключается на этапе 7.

Документация: [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

### Вход в мобильном приложении

OIDC Authorization Code + PKCE: вход открывается в системном браузере, приложение получает код
через callback, PKCE защищает обмен кода от перехвата, токены хранятся в защищённом хранилище
платформы. Встроенный WebView для входа не используется.

Документация: [RFC 8252 — OAuth для native apps](https://www.rfc-editor.org/rfc/rfc8252.html),
[RFC 7636 — PKCE](https://www.rfc-editor.org/rfc/rfc7636.html),
[OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html),
[RFC 9700 — безопасность OAuth 2.0](https://www.rfc-editor.org/rfc/rfc9700.html),
[Android Keystore](https://developer.android.com/privacy-and-security/keystore).

## Практика

1. Реализовать один базовый сценарий регистрации/входа с готовой библиотекой хеширования пароля
   и серверной сессией. У каждой сессии есть срок действия и возможность отзыва.
2. Cookie: HttpOnly, Secure, подходящий SameSite; CSRF-защита для cookie-auth, проверки Origin
   и настройки доверенного reverse proxy. Уметь объяснить модель угроз.
3. Ограничить частоту попыток входа; отвечать так, чтобы не раскрывать наличие аккаунта.
   Секреты и сессионные токены не попадают в логи.
4. Добавить выход из одной/всех сессий и восстановление доступа через одноразовый ограниченный
   по времени токен. Письмо идёт в локальный email sink. Проверить повторное использование токена.
5. Привязать данные к владельцу. Проверять доступ и при чтении, и при изменении,
   и в агрегатах/экспорте, а не только при загрузке страницы.
   - Если связь с пользователем не заложена на этапе 1, она добавляется миграцией вместе
     с переносом существующих учебных записей.
6. Провести негативные API-тесты с двумя пользователями: подмена ID, отсутствие сессии,
   истёкшая/отозванная сессия, попытка передать чужого владельца в PATCH.
   - Удобно составить таблицу «эндпоинт × сценарий» и закрыть каждую ячейку тестом
     или осознанным решением.
7. Нарисовать мобильный вход через OIDC Authorization Code + PKCE: системный браузер, callback,
   серверная проверка и хранение токенов в защищённом хранилище платформы. Сравнить с веб-сессией;
   полноценный native-клиент на этом этапе не обязателен.
8. После проверок выполнить первый приватный HTTPS-деплой на доступную тестовую среду.
   Можно пройти краткую часть [этапа 8](08-deploy-operations.md) заранее, засчитав время один раз.

## Критерии выхода

- Чужая запись недоступна даже при известном ID.
- Выход и отзыв реально прекращают доступ.
- Понятна разница между учебной реализацией auth и стоимостью её поддержки в продукте.

## Типичные ошибки

- `userId` или `ownerId` берётся из тела запроса.
- Владение проверяется только при чтении по ID, а список, агрегаты и экспорт его не учитывают.
- JWT в `localStorage` выбран по умолчанию, и сессию невозможно отозвать.
- Разные ответы для «нет такого пользователя» и «неверный пароль».
- Токены и ссылки восстановления в логах.
- Сессии остаются активными после смены пароля.

## Что записать как доказательство

Негативные API-тесты с двумя пользователями, проверка повторного использования токена
восстановления, схема мобильного входа, ссылка на приватный HTTPS-деплой.

Читать: [OWASP — управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
