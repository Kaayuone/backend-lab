# Этап 9. Небольшой SaaS и платежи

[Маршрут](../ROADMAP.md) · [← Этап 8](08-deploy-operations.md) · [Этап 10 →](10-performance-final.md)

**Оценка:** 36–48 часов. **Проект:** [Feedback Inbox](../PROJECTS.md#проект-3-feedback-inbox--обратная-связь-для-своих-приложений).
**Нужно до начала:** авторизация этапа 4, идемпотентность этапа 5, интеграции этапа 7,
выпуск этапа 8.

**Результат:** Feedback Inbox с двумя изолированными workspace и тестовым платным тарифом.

Примерный бюджет внутри этапа: 8–10 часов на продуктовый сценарий и tenant isolation, 6–8 на
billing-модель, 12–18 на провайдера/webhooks, 10–12 на отказы, UI и выпуск. Если sandbox
провайдера требует недоступное оформление, сначала сделать fake gateway; интеграция с настоящим
sandbox остаётся открытым критерием, а не считается выполненной.

## Зачем этот этап

SaaS добавляет два класса риска: утечку данных между клиентами и расхождение денег и прав.
Платёж — распределённая система через сеть: уведомление приходит с опозданием, дважды, не по
порядку или не приходит совсем, а браузер пользователя может закрыться на любом шаге. Цель —
изоляция tenant во всех путях доступа и платёжный сценарий с журналом состояний и сверкой.

## Что разобрать

### Изоляция клиентов

Tenant определяется на сервере: по membership пользователя или по public project key, в
зависимости от endpoint. Переданный клиентом `workspaceId` не является разрешением. Проверка
нужна в запросах, файлах, агрегатах и фоновых задачах. Row-Level Security в PostgreSQL —
дополнительный уровень защиты, но не замена проверкам в приложении и тестам.

Документация: [OWASP Multi-Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html),
[OWASP IDOR](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html),
[Row-Level Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

### Billing и права доступа

Платёж — факт движения денег. Покупка или подписка — коммерческое соглашение. Право доступа
(entitlement) — что пользователь может делать сейчас, с периодом действия и основанием.
Смешивание этих понятий в булевой колонке `isPaid` не позволяет корректно обработать возврат,
истечение срока и повторную покупку.

Документация: [Entitlements в Stripe](https://docs.stripe.com/billing/entitlements) — пример
разделения понятий.

### Создание платежа

Цена, валюта, товар и пользователь определяются сервером; данные карты обрабатывает провайдер
на своей checkout-странице. Платёж создаётся с ключом идемпотентности, а ID провайдера и
собственный ID сохраняются до перехода клиента на оплату.

Документация: [процесс платежа ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process),
[формат взаимодействия и идемпотентность ЮKassa](https://yookassa.ru/developers/using-api/interaction-format),
[Stripe Checkout](https://docs.stripe.com/payments/checkout),
[идемпотентные запросы Stripe](https://docs.stripe.com/api/idempotent_requests).

### Webhooks и состояния

Подлинность уведомления проверяется способом конкретного провайдера: у Stripe — подписью,
у ЮKassa — способами из её документации (проверка источника, запрос актуального статуса
объекта через API). Событие сначала надёжно записывается и дедуплицируется по уникальному
идентификатору, затем переход состояния и выдача права выполняются атомарно. Порядок прихода
событий не является порядком событий: решение принимается по состоянию объекта у провайдера.
Возврат браузера на сайт оплату не подтверждает.

Документация: [webhooks ЮKassa](https://yookassa.ru/developers/using-api/webhooks),
[webhooks Stripe](https://docs.stripe.com/webhooks), [возвраты Stripe](https://docs.stripe.com/refunds).

### Сверка и время

Периодическая или ручная сверка доводит незавершённые платежи до актуального состояния через
API провайдера: потерянный webhook не должен оставлять оплату в неизвестном состоянии.
Срок доступа проверяется по серверному времени при каждом обращении; таймер — не единственная
проверка. Тесты используют управляемые часы.

Документация: [тестирование ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing),
[тестирование Stripe](https://docs.stripe.com/testing),
[test clocks Stripe](https://docs.stripe.com/billing/testing/test-clocks),
[управляемое время в Vitest](https://vitest.dev/guide/mocking/timers).

## Сделать

1. Перенести понятный каркас, сессии, тестовую БД, логи и deployment-шаблон.
   Написать только новую предметную часть из [PROJECTS.md](../PROJECTS.md).
2. Добавить workspace, membership и минимальные роли owner/member. Проверять tenant во всех
   запросах, файлах, агрегатах и фоновых задачах. Роль берётся на сервере.
3. Создать Free/Pro и отдельное понятие права доступа. Не смешивать платёж, подписку и разрешение
   использовать функцию в одну булеву колонку `isPaid`.
4. Начать с разовой покупки 30 дней Pro через размещённую у провайдера checkout-страницу.
   Цена, валюта, товар и пользователь определяются сервером. Данные карты обрабатывает провайдер.
5. Создать платёж идемпотентно. Сохранить provider ID и собственный ID до перехода клиента;
   при неизвестном результате повторять по договорённости провайдера, а не создавать новый платёж.
6. Принимать webhook по правилам конкретного провайдера: подпись/проверка источника/запрос
   состояния через API. Не переносить способ проверки Stripe на любой другой сервис.
7. Надёжно зафиксировать событие, дедуплицировать по уникальному идентификатору, обработать
   переход состояния и выдачу права атомарно. Возврат браузера не подтверждает оплату.
8. Обработать повторы, события не по порядку, неизвестный payment ID, неверные сумму/валюту,
   отмену, полный возврат и истечение доступа. Таймер не должен быть единственной проверкой срока.
9. Добавить периодическую/ручную сверку незавершённых платежей с провайдером.
   Потерянный webhook не должен оставлять оплату навсегда в неизвестном состоянии.
10. Отдельно отработать повторное продление и неуспешное продление через fake gateway/fixtures.
    Реальные автосписания, prorations, купоны и несколько провайдеров оставить расширением.

Правила MVP для каждого платёжного события собраны в [PROJECTS.md](../PROJECTS.md).

## Обязательные проверки

- Два одинаковых webhook дают одно право.
- Событие с меньшей актуальностью не отменяет уже подтверждённый более новый результат.
- Refund после оплаты приводит к явно описанной политике доступа.
- Параллельное создание последнего разрешённого ресурса не превышает квоту.
- Пользователь одного workspace не читает другой.

## Критерии выхода

- Платежи работают в sandbox.
- Есть журнал состояний и способ сверки.
- Объясняешь отличие billing от entitlements и почему сеть не даёт exactly-once.

## Выбор провайдера

Провайдер выбирается по доступности для продавца и продукта, например
[ЮKassa](https://yookassa.ru/developers/using-api/webhooks) или
[Stripe](https://docs.stripe.com/webhooks). Изучается один провайдер. Перед реальным приёмом денег
отдельно проверить его текущие условия, оформление продавца, чеки/налоги и ограничения продукта.
Правила мобильных магазинов изучать при запуске в них.

## Типичные ошибки

- Pro выдаётся по возврату браузера со страницы оплаты.
- Сумма или валюта берутся из запроса клиента.
- Обработчик webhook выполняет тяжёлую работу синхронно или не идемпотентен.
- Порядок прихода событий считается порядком их возникновения.
- Возврат одного платежа отзывает все основания доступа пользователя.
- При понижении тарифа удаляются проекты и обращения.

## Что записать как доказательство

Журнал состояний платежа в sandbox, тесты пяти обязательных проверок, сценарий сверки после
потерянного webhook, тесты изоляции workspace.
