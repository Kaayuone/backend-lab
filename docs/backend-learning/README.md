# Бэкенд для собственных продуктов: границы и маршрут

Дата: 2 октября 2026 года. Статус: актуальный план.

План составлен заново по целям разработчика. Прежние планы v2/v3 остаются историческими
материалами: их этапы, сроки и привязка к автомобильному приложению сюда не переносятся.
Наличие кода в `old/garage-rest-api` не означает автоматического прохождения нового этапа.

## Исходная точка и результат

Разработчик уровня middle+/senior во фронтенде. JavaScript/TypeScript и создание интерфейсов
не требуют повторного вводного курса. Есть небольшой опыт NestJS, знакомство с SQL и Docker;
написание запросов и устройство серверных систем требуют практики.

Главная цель — самостоятельно создавать и запускать SaaS и серверную часть мобильных
приложений. Дополнительная — сохранить возможность перейти в fullstack/backend на
русскоязычном рынке, желательно удалённо независимо от региона. Удалённая вакансия сама
по себе не гарантирует работу из любой страны: это проверяется отдельно у работодателя.

После программы разработчик умеет довести небольшое приложение от модели данных до
работающего сервиса, объяснить его ограничения и восстановить после типового сбоя.
Это не обещание определённого грейда или трудоустройства.

«80–90% задач» здесь означает охват распространённых классов задач выбранных продуктов,
а не статистически измеренную долю всего бэкенда.

## Глубина и границы

**Освоить практически:** SQL, транзакции, HTTP API, авторизация, проверки входных данных,
работа с отказами внешних сервисов, очереди, тестирование, веб-платёж в sandbox.

**Понимать и один раз пройти руками:** DNS/TLS/reverse proxy, Linux-процессы и права,
деплой, восстановление БД, базовая наблюдаемость, OIDC/PKCE для мобильного клиента,
масштабирование API и worker как отдельных процессов.

**Оставить до конкретной потребности:** Kubernetes, микросервисы, Kafka, service mesh,
event sourcing, сложный DDD/CQRS, GraphQL/gRPC, несколько основных БД, шардирование,
мультирегиональность, собственный OAuth-сервер, продвинутая DBA/SRE-работа.
Понимать назначение достаточно; устанавливать эти технологии для галочки не нужно.

Offline-first синхронизация, разрешение конфликтов, realtime-игровой сервер и магазинные
подписки мобильных платформ — отдельные расширения. Обычное мобильное приложение с API
входит в базу. Наличие REST API не решает автоматически offline-sync или правила оплаты
цифровых товаров в магазинах приложений.

При 10 часах в неделю это 25–34 учебные недели; с запасом около 20% — примерно 30–41 неделя,
то есть 7–10 месяцев. При 8 часах в неделю с таким запасом — около 9–12 месяцев.
10 часов — верхний ориентир, а не обязательство. Пропущенная неделя сдвигает маршрут.

Ранние полезные результаты: приватная версия проекта 1 после этапа 4 (106–140 часов),
работающий бот после этапа 6 (154–206 часов). Прототип бота возможен раньше, но завершённым
он считается после проверки очереди, отказов и ограничений ресурсов.

## Учебный ритм

Обычная неделя: 2 часа на механизм и документацию, 5 на реализацию, 2 на эксперименты/тесты,
1 на повторение и запись выводов. Распределение можно менять, сохраняя практику и проверку.

Цикл для новой темы: сформулировать проблему → предсказать поведение → реализовать →
воспроизвести отказ → объяснить наблюдение → закрепить важный контракт тестом.
Для одноразового эксперимента достаточно воспроизводимого сценария и результата;
автотест на каждый прочитанный пункт не требуется.

Перед переходом дальше нужно без подсказки объяснить основные решения, выполнить
критерии этапа и показать работающий сценарий. Если это уже получается на текущем коде,
этап сокращается. Переписывать понятный CRUD ради нового названия проекта не нужно.

## Как использовать AI и готовые решения

- UI, стили, фикстуры, типовой каркас и повторяющуюся настройку можно генерировать.
- Новый SQL-запрос, транзакцию, правило доступа и обработку webhook сначала спроектировать
  самостоятельно. Затем использовать AI для ревью, альтернатив и поиска пропущенных отказов.
- После помощи уметь объяснить каждое значимое условие и изменить его под новый сценарий.
- Тест должен проверять наблюдаемое поведение; копирование реализации в ожидания ничего не доказывает.
- Библиотеки шифрования, паролей, платёжный SDK и медиазагрузчик использовать готовые.

## Организация практики в репозитории

Будущие проекты можно размещать в `projects/spendboard`, `projects/audio-bot`,
`projects/feedback-inbox`, короткие эксперименты — в `labs`. Это предлагаемая структура;
эти каталоги и приложения данным изменением документации не создаются.

У проектов отдельные конфигурации и базы. Сначала достаточно независимых `package.json`;
переход к workspace/монорепо оправдан только реальным общим кодом. После первого проекта
сохранить минимальный шаблон запуска, тестов, логов и миграций. Не создавать универсальный
фреймворк для трёх упражнений. Предметные таблицы и правила между ними не смешивать.

`old/garage-database` и `old/garage-rest-api` остаются источником уже написанных упражнений.
Их рефакторинг, перенос данных и завершение старого плана не являются предварительным условием.
