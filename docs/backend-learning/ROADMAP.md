# Подробная программа

[К границам и оценке времени](README.md) · [Стек](STACK.md) · [Проекты](PROJECTS.md) · [Прогресс](PROGRESS.md)

Порядок построен по зависимостям навыков. Критерии выхода проверяют самостоятельность,
а не число просмотренных уроков. Все оценки включают реализацию соответствующей части проекта.
Проекты описаны отдельно, чтобы требования к приложению не повторялись в каждом этапе.

## Этап 0. Диагностика и среда — 6–8 часов

**Цель:** установить фактическую исходную точку и отделить учебные данные от ценных.

Сделать:

1. Нарисовать путь `клиент → DNS → HTTPS → сервер → пул соединений → БД → ответ`.
   Отметить, на каких участках возможны таймаут, отказ и утечка данных.
2. Без AI написать SELECT с JOIN и агрегацией; объяснить FK, UNIQUE и транзакцию.
   Документацией пользоваться можно. Пробелы записать в [PROGRESS.md](PROGRESS.md).
3. Подготовить изолированные учебную и тестовую БД, понять connection string, порт,
   Docker network и volume. Проверить подключение из приложения и pgAdmin/psql.
4. Взять понятные части текущего Nest-кода как примеры. Не тратить этот этап на уборку
   всего репозитория и завершение прежних задач.
5. Зафиксировать версии runtime, команды запуска и принцип обращения с `.env`.
   Настроить форматирование, lint и проверку типов минимального учебного проекта.

**Эксперимент:** остановить учебную БД, сравнить ошибку подключения с неверным паролем;
перезапустить контейнер и проверить сохранность данных в volume.

**Выход:** объясняешь, где живут данные, каким пользователем приложение входит в БД,
почему тесты не должны подключаться к dev/prod. Диагностика не выставляет грейд.

## Этап 1. SQL и модель данных — 30–40 часов

**Результат:** база проекта Spendboard без HTTP и без ORM.

Разобрать последовательно:

- Таблица, строка, ключ; связи 1:N/N:M; нормализация на прикладных примерах.
- `NULL`, трёхзначная логика, `DEFAULT`, `NOT NULL`, `CHECK`, `UNIQUE`, FK,
  поведение удаления. Где правило должно защищаться самой БД.
- INSERT/UPDATE/DELETE с RETURNING; JOIN, GROUP BY, HAVING, EXISTS,
  подзапросы и CTE. Один полезный пример оконной функции.
- Деньги: точная десятичная арифметика или minor units, код валюты,
  явное округление; безопасное представление BIGINT/NUMERIC на границе JS.
- `date` и `timestamptz`: календарная дата отличается от момента времени;
  отображение/группировка в выбранном часовом поясе.
- BEGIN/COMMIT/ROLLBACK; атомарность нескольких изменений.
- Индексы, порядок колонок составного индекса, селективность,
  цена индекса для записи. Первое чтение EXPLAIN.
- Миграции и отдельные dev seed/тестовые фикстуры.

Практика на `projects`, `expenses`, `recurring_costs`:

1. Спроектировать таблицы и объяснить каждый FK/UNIQUE/CHECK.
2. Написать 10–12 содержательных запросов: расходы за период, итоги по проектам и валютам,
   проекты без расходов, топ категорий, ближайшие даты продления, накопительный итог.
   Не суммировать разные валюты в одно число без явно заданного курса.
3. Проверить пограничные данные: пустая выборка, одинаковые даты, NULL, удаляемый проект,
   отрицательная сумма, большая сумма, разные валюты и конец месяца.
4. Создать схему миграцией на пустой БД; отдельной миграцией добавить новое поле и индекс.
   Выполнить обновление БД, в которой уже есть тестовые записи.
5. Сохранить запросы и ожидаемые результаты. Несколько ключевых ограничений и агрегаций
   закрепить интеграционными тестами; однотипные SELECT не превращать в десятки тестов.

**Эксперименты:** FK против предварительного SELECT в приложении; ошибка на второй записи
в транзакции; изменение плана запроса на достаточно большом наборе данных до/после индекса.

**Выход:** самостоятельно пишешь JOIN/агрегацию, не устраняешь случайное размножение строк
через DISTINCT без понимания причины; объясняешь выбор типов и ограничения модели.

Читать по теме: [учебник PostgreSQL](https://www.postgresql.org/docs/current/tutorial.html).
SQL остаётся регулярной практикой в последующих проектах.

## Этап 2. HTTP, сеть и Node.js — 18–24 часа

**Цель:** понимать, что фреймворк делает поверх сети и runtime.

Разобрать:

- HTTP methods, status codes, headers, cookies, body; безопасные и идемпотентные операции.
- Различие сетевой ошибки и HTTP-ошибки; DNS, TCP, TLS и reverse proxy на уровне пути запроса.
- Keep-alive, ограничение размера запроса, connect/response/overall timeout.
- REST-ресурсы, пагинация и стабильная сортировка; контракт ошибок; совместимость API.
- CORS как ограничение браузера, а не механизм авторизации.
- Node event loop, microtasks, libuv worker pool, I/O и CPU; Promise не создаёт поток CPU.
- Потоки и backpressure; ограниченный параллелизм, AbortSignal и завершение процесса.
- ESM, сборка TS, env и зависимости только в объёме, нужном для запуска сервера.

Практика — короткие лабораторные, без второго полноценного фреймворка:

1. Сделать минимальный HTTP-сервер с двумя маршрутами через Node `http`; закончить за 2–3 часа.
2. Отправить корректный и некорректный запрос через `curl.exe`/HTTP-клиент, увидеть сырые ответы.
3. Сравнить CPU-цикл и ожидающий I/O запрос: во время каждого вызвать простой health endpoint.
4. Передать большой локальный файл потоком и через чтение целиком; сравнить память.
5. Вызвать управляемую заглушку внешнего API: быстрый ответ, медленный ответ, 429 и 500.
   Добавить общий дедлайн и ограничение параллельных обращений.

**Выход:** объясняешь, почему `async` не спасает от блокировки CPU; умеешь ограничить время
и объём операции; по сообщению и логам различаешь ошибку приложения, БД и сети.

Читать: [Node.js: не блокировать event loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop).

## Этап 3. NestJS, API и тесты — 28–36 часов

**Результат:** Spendboard локально выполняет полезные сценарии и имеет минимальный UI.

Разобрать controllers/providers/modules, DI, guards/pipes/filters/interceptors и жизненный
цикл запроса. Каждый механизм внедрять для понятной задачи: валидация входа, обработка
ошибки или измерение запроса. Не создавать общий base service для всего CRUD.

Сделать:

1. Описать 5–7 сценариев и API-контракт: создание расхода, исправление, список, фильтр,
   итоги, ближайшие продления. Добавить OpenAPI и пример ошибки.
2. Разделить HTTP DTO, бизнес-операцию и доступ к БД. Осознанно решить, где нужен repository,
   а где дополнительный интерфейс только усложнит код.
3. Подключить Kysely; сравнить несколько запросов с SQL этапа 1. Типизация запроса не заменяет
   runtime-валидацию body/query/env и не проверяет сама по себе актуальность схемы БД.
4. Настроить единый формат ошибок с кодом, сообщением и request ID. Ошибки БД и stack trace
   не выдавать клиенту; внутренние подробности оставлять в защищённых логах.
5. Реализовать лимиты пагинации, whitelist сортировки, явные правила PATCH и обработки NULL.
6. Валидировать конфигурацию при старте, добавить структурированные логи с redaction,
   health/readiness и корректное закрытие пула при завершении.
7. Сделать простой UI через AI; API должно оставаться полностью проверяемым без него.
8. Собрать контейнер и поднять API + PostgreSQL через Compose локально.

Тестовый минимум:

- Unit-тест для нетривиального расчёта/преобразования.
- Integration-тест запросов и ограничений на настоящем PostgreSQL.
- API-тест успешного сценария, плохого ввода, отсутствующего объекта и пагинации.
- Отдельный `TEST_DATABASE_URL`, проверка разрешённой тестовой БД, миграции и fixtures.
  Setup/teardown должны завершаться с `await`; тесты не используют реальные личные данные.

**Эксперимент:** пересоздать только одноразовую тестовую БД и запустить suite с нуля;
изменить контракт ошибки и увидеть, какой тест защищает клиента.

**Выход:** приложение запускается по README; данные переживают перезапуск; важные сценарии
проверены автоматически. Покрытие в процентах не является критерием завершения.

Читать выборочно: [NestJS](https://docs.nestjs.com/) и [Kysely](https://kysely.dev/docs/intro).

## Этап 4. Учётные записи и безопасность — 24–32 часа

**Результат:** приватное приложение с корректными границами доступа.

Изучить различие authentication/authorization; идентичность пользователя, владение объектом,
роль и разрешение. Пользователь определяется по проверенной сессии, а не по `userId` из body.

Практика:

1. Реализовать один базовый сценарий регистрации/входа с готовой библиотекой хеширования
   пароля и серверной сессией. У каждой сессии есть срок действия и возможность отзыва.
2. Cookie: HttpOnly, Secure, подходящий SameSite; CSRF-защита для cookie-auth,
   проверки Origin и настройки доверенного reverse proxy. Уметь объяснить модель угроз.
3. Ограничить частоту попыток входа; отвечать так, чтобы не раскрывать наличие аккаунта.
   Секреты и сессионные токены не попадают в логи.
4. Добавить выход из одной/всех сессий и восстановление доступа через одноразовый
   ограниченный по времени токен. На этом этапе письмо идёт в локальный email sink;
   реальный транспорт появится на этапе 7. Проверить повторное использование токена.
5. Привязать данные к владельцу. Проверять доступ и при чтении, и при изменении,
   и в агрегатах/экспорте, а не только при загрузке страницы.
6. Провести негативные API-тесты с двумя пользователями: подмена ID, отсутствие сессии,
   истёкшая/отозванная сессия, попытка передать чужого владельца в PATCH.
7. Нарисовать мобильный вход через OIDC Authorization Code + PKCE: системный браузер,
   callback, серверная проверка и хранение токенов в защищённом хранилище платформы.
   Сравнить с веб-сессией; полноценный native-клиент на этом этапе не обязателен.
8. После проверок выполнить первый приватный HTTPS-деплой на доступную тестовую среду.
   Можно пройти краткую часть этапа 8 заранее, засчитав время один раз.

**Выход:** чужая запись недоступна даже при известном ID; выход/отзыв реально прекращают
доступ; понятна разница между учебной реализацией auth и стоимостью её поддержки в продукте.

Читать: [OWASP: управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
Публичная регистрация, MFA и несколько социальных провайдеров не обязательны для первого проекта.

## Этап 5. Транзакции, гонки и идемпотентность — 16–22 часа

**Цель:** сохранять правила при параллельных запросах и повторах клиента.

Разобрать Read Committed, MVCC на прикладном уровне, lost update, блокировку строки,
deadlock и порядок взятия блокировок. Сравнить optimistic concurrency, условный UPDATE,
UNIQUE и SELECT FOR UPDATE. Понимать, когда нужен более строгий уровень изоляции.

Практика:

1. В Spendboard добавить `version` для редактируемого расхода и конфликт при устаревшем
   изменении. Два клиента не должны молча терять правки друг друга.
2. В отдельной маленькой лабораторной дать двум запросам последнее доступное место/единицу
   квоты. Сначала воспроизвести нарушение, затем защитить инвариант транзакцией или атомарным SQL.
3. Для одной составной операции вызвать ошибку после первого изменения и доказать rollback.
4. Смоделировать повтор запроса после неизвестного результата. Реализовать idempotency key:
   область пользователя/операции, уникальность, сравнение payload и повтор результата.
5. Показать разницу между дедупликацией запроса, идемпотентной операцией и повторной
   отправкой ответа. TTL записи выбирать по договорённости, а не случайной константой.

**Эксперименты:** два независимых соединения к БД и управляемый барьер запуска;
конфликт версий; одинаковый ключ с другим payload; lock timeout.
Не доказывать отсутствие гонки одним удачным последовательным запуском.

**Выход:** объясняешь, почему проверка SELECT перед INSERT не заменяет UNIQUE,
не держишь DB-транзакцию открытой во время запроса к внешнему сервису, умеешь выбрать
самый простой способ защиты конкретного инварианта.

Читать по эксперименту: [PostgreSQL: уровни изоляции](https://www.postgresql.org/docs/current/transaction-iso.html).

## Этап 6. Telegram-бот, очередь и worker — 32–44 часа

**Результат:** Audio Bot из [задания проекта](PROJECTS.md), работающий для личного использования.

Новые темы: polling/webhook, повторная доставка update, быстрый приём задачи,
Redis/BullMQ, backoff/jitter, конечное число попыток, worker concurrency,
завершение subprocess, временные файлы и состояние длительной операции.

Порядок реализации:

1. Через grammY принять ссылку только от разрешённых Telegram ID; показать статус задачи.
   Начать с polling. Для webhook изучить HTTPS и secret token, не поддерживать оба способа одновременно.
2. Сначала сделать адаптер, который возвращает маленький локальный аудиофайл.
   Это отделяет проверку приложения от нестабильности внешнего источника.
3. Вынести долгую работу в BullMQ worker. В БД хранить задание и его состояния;
   обработчик update только проверяет вход и надёжно фиксирует принятие.
4. Разобрать разрыв «записали задачу в БД, но не положили в Redis». Реализовать небольшой
   outbox/dispatcher: запись задания и намерения отправки в одной DB-транзакции,
   повторная отправка с устойчивым ID, идемпотентный worker. Брокер может доставить задачу повторно.
5. Подключить yt-dlp/FFmpeg через `spawn` с массивом аргументов и без shell.
   Для каждого задания отдельный временный каталог, фиксированные параметры и таймаут.
6. Ограничить вход, длительность, размер, число одновременных работ, диск, CPU/память
   контейнера. Отменять или завершать зависший дочерний процесс вместе с его потомками.
7. Разделить повторяемые сетевые ошибки и постоянные отказы: удалённый ресурс,
   неподдерживаемая ссылка, слишком большой файл. Показать пользователю понятный результат.
8. Отправить аудио в Telegram; записать статус доставки и удалить временные файлы.
   Очистка выполняется и после ошибки; отдельная уборка удаляет остатки после аварии процесса.

Для Redis очереди проверить сохранение данных и политику `noeviction`. В БД остаётся
источник состояния задач: сверка должна находить принятые, но потерянные очередью задания
и зависшие попытки. Восстановление Redis не заменяет идемпотентность обработки.
Настройки соединений и Redis: [BullMQ](https://docs.bullmq.io/guide/connections).

**Эксперименты:** перезапуск worker посреди обработки; недоступный Redis после commit;
два одинаковых update; повтор задачи после завершения; переполнение лимита;
таймаут при отправке результата в Telegram.

**Выход:** API/бот отвечают во время конвертации; принятая задача не теряется в разрыве
БД/очередь; повтор не создаёт несколько вычислений без необходимости; после сбоя нет
вечного `processing` и забытых файлов. Не обещать exactly-once для внешней отправки:
таймаут Telegram может оставить неизвестным, доставлено ли сообщение.

Читать: [grammY](https://grammy.dev/guide/),
[BullMQ: идемпотентные задачи](https://docs.bullmq.io/patterns/idempotent-jobs),
[yt-dlp](https://github.com/yt-dlp/yt-dlp). Подробные ограничения медиа — в задании проекта.

## Этап 7. Файлы и внешние интеграции — 16–22 часа

**Цель:** перестать считать внешнюю систему надёжной частью собственного процесса.

1. Добавить временный приватный архив результатов Audio Bot в S3-совместимом хранилище.
   Метаданные и владелец — в PostgreSQL, содержимое — в object storage, у объекта есть срок жизни.
   Доступ выдаётся после авторизации через короткую подписанную ссылку.
2. Пройти маленькую лабораторную прямой загрузки: согласовать размер/тип/ключ,
   проверить фактический объект перед публикацией; очистить загрузку, для которой
   пользователь так и не завершил подтверждение. Не доверять одному Content-Type клиента.
3. Для скачивания не читать целый файл в память. Разобрать имя файла, случайный object key,
   Content-Disposition, ограничения размера и приватность bucket.
4. Подключить email-транспорт для готового восстановления доступа из этапа 4.
   Проверки приложения используют fake/sink, отдельный smoke проверяет настоящий транспорт.
5. В общем HTTP-клиенте ограничить время, число попыток и конкурентность;
   учитывать 429/Retry-After. Повтор неидемпотентного запроса требует отдельного решения.
6. Проверить SSRF и опасность произвольного URL: scheme/host, редиректы, DNS,
   доступ к loopback/private/link-local адресам. Одной проверки строки URL недостаточно.

**Эксперименты:** файл удалён до выдачи; подписанная ссылка истекла; сервис отвечает 429;
соединение оборвалось после отправки запроса; внешний ответ не соответствует ожидаемой схеме.

**Выход:** умеешь разделить ошибку транспорта и доменный отказ, ограничить стоимость операции,
не выдаёшь чужие файлы, имеешь способ убрать бесхозные объекты. Провайдер хранится за небольшим
адаптером, а не за универсальной абстракцией всех облаков.

## Этап 8. Деплой и эксплуатация — 26–36 часов

**Результат:** понятный полный цикл выпуска, без отдельной специализации DevOps.

Практика на уже работающем проекте:

1. Linux: SSH-ключи, пользователи/права, процессы, переменные окружения, дисковое место,
   логи, listening ports и firewall. Уметь выяснить, почему процесс не запускается.
2. Собрать production-образ: фиксированная база/lockfile, multi-stage где полезно,
   non-root процесс, минимальные зависимости, секреты вне image.
3. Compose: API/worker/PostgreSQL/Redis и reverse proxy, внутренние сети и volumes.
   Наружу публикуются необходимые порты; БД и Redis не становятся публичными сервисами.
4. Домен → DNS → Caddy → HTTPS → приложение. Разобрать forwarded headers,
   доверенный proxy, ограничения размера и времени HTTP-запроса.
5. CI: установка из lockfile, lint/typecheck, тесты с одноразовой БД, сборка image.
   Затем контролируемый выпуск конкретного image tag и smoke-проверка.
6. Миграции выполнять отдельным шагом выпуска, а не одновременно из каждого API-процесса.
   На учебном изменении пройти expand → совместимый код → перенос данных → contract.
7. Проверить rollback приложения при совместимой схеме. Откат image не восстанавливает
   удалённые данные; разрушительную миграцию нельзя считать автоматически обратимой.
8. Записать backup/restore-процедуру: отдельное хранилище, доступ, периодичность, срок хранения,
   RPO/RTO простыми словами. Восстановить backup в новую БД и проверить прикладные записи.
9. Настроить логи, uptime, ошибки, latency, длину/возраст очереди, диск и число соединений БД.
   Для одного проекта достаточно небольшого набора метрик и одного полезного уведомления.
10. Описать runbook: недоступен API; недоступна БД; worker завис; закончился диск;
    не проходит webhook; нужно отозвать утёкший токен.

**Эксперименты:** перезапустить хост/контейнер; оборвать БД; выпустить несовместимую
настройку в тестовой среде; выполнить восстановление и измерить время.

**Выход:** другой человек может запустить проект по README; ты находишь причину сбоя
по наблюдениям, выкатываешь известную версию и подтверждаешь восстановление данных.
Backup считается проверенным только после успешного restore.

При отсутствии VPS сначала использовать Linux VM локально, а внешний HTTPS/webhook проверить
через доступную тестовую среду. Не считать публичный деплой пройденным до реального выполнения.
Выбор хостинга, стоимость и покупка домена — отдельные решения перед этим этапом.

Читать: [Docker Compose в production](https://docs.docker.com/compose/how-tos/production/) и
[Caddy HTTPS](https://caddyserver.com/docs/automatic-https).

## Этап 9. Небольшой SaaS и платежи — 36–48 часов

**Результат:** Feedback Inbox с двумя изолированными workspace и тестовым платным тарифом.

Примерный бюджет внутри этапа: 8–10 часов на продуктовый сценарий и tenant isolation,
6–8 на billing-модель, 12–18 на провайдера/webhooks, 10–12 на отказы, UI и выпуск.
Если sandbox провайдера требует недоступное оформление, сначала сделать fake gateway;
интеграция с настоящим sandbox остаётся открытым критерием, а не считается выполненной.

Сделать:

1. Перенести понятный каркас, сессии, тестовую БД, логи и deployment-шаблон.
   Написать только новую предметную часть из [PROJECTS.md](PROJECTS.md).
2. Добавить workspace, membership и минимальные роли owner/member. Проверять tenant
   во всех запросах, файлах, агрегатах и фоновых задачах. Роль берётся на сервере.
3. Создать Free/Pro и отдельное понятие права доступа. Не смешивать платёж, подписку
   и разрешение использовать функцию в одну булеву колонку `isPaid`.
4. Начать с разовой покупки 30 дней Pro через размещённую у провайдера checkout-страницу.
   Цена, валюта, товар и пользователь определяются сервером. Данные карты обрабатывает провайдер.
5. Создать платёж идемпотентно. Сохранить provider ID и собственный ID до перехода клиента;
   при неизвестном результате повторять по договорённости провайдера, а не создавать новый платёж.
6. Принимать webhook по правилам конкретного провайдера: подпись/проверка источника/запрос
   состояния через API. Не переносить способ проверки Stripe на любой другой сервис.
7. Надёжно зафиксировать событие, дедуплицировать по уникальному идентификатору,
   обработать переход состояния и выдачу права атомарно. Возврат браузера не подтверждает оплату.
8. Обработать повторы, события не по порядку, неизвестный payment ID, неверные сумму/валюту,
   отмену, полный возврат и истечение доступа. Таймер не должен быть единственной проверкой срока.
9. Добавить периодическую/ручную сверку незавершённых платежей с провайдером.
   Потерянный webhook не должен оставлять оплату навсегда в неизвестном состоянии.
10. Отдельно отработать повторное продление и неуспешное продление через fake gateway/fixtures.
    Реальные автосписания, prorations, купоны и несколько провайдеров оставить расширением.

**Обязательные проверки:** два одинаковых webhook дают одно право; событие с меньшей
актуальностью не отменяет уже подтверждённый более новый результат; refund после оплаты
приводит к явно описанной политике доступа; параллельное создание последнего разрешённого
ресурса не превышает квоту; пользователь одного workspace не читает другой.

**Выход:** платежи работают в sandbox, есть журнал состояний и способ сверки;
ты можешь объяснить отличие billing от entitlements и почему сеть не даёт exactly-once.

Первичный выбор провайдера делается по доступности для продавца и продукта: например,
[ЮKassa](https://yookassa.ru/developers/using-api/webhooks) или
[Stripe](https://docs.stripe.com/webhooks). Изучается один провайдер.
Перед реальным приёмом денег отдельно проверить его текущие условия, оформление продавца,
чеки/налоги и ограничения продукта. Правила мобильных магазинов изучать при запуске в них.

## Этап 10. Производительность и итоговая проверка — 18–26 часов

**Цель:** понять пределы своего решения и принимать решения на основании измерений.

1. Выбрать один пользовательский запрос и одну фоновую задачу. Зафиксировать размер данных,
   среду, профиль нагрузки, p50/p95, ошибки, throughput, CPU/память и соединения БД.
2. Найти медленный SQL через EXPLAIN ANALYZE на тестовых данных: N+1, ненужный JOIN,
   полное сканирование, неправильный индекс, слишком большая выдача.
3. Сравнить offset и cursor pagination на изменяемом списке со стабильным порядком.
4. Провести один эксперимент с кэшем: ключ, TTL, tenant, инвалидирование и устаревший ответ.
   Оставить кэш в приложении только если есть измеренная польза.
5. Показать, что увеличение числа API-процессов меняет общий размер DB-пула и лимиты.
   Backpressure/лимит worker важнее бесконечного накопления задач.
6. Прочитать метрики и логи одного сквозного запроса/задачи; понять назначение trace,
   не разворачивая обязательный большой observability-стек.
7. Пройти итоговый сценарий: новый пользователь → ресурс → фоновая работа → тестовая
   оплата → повтор уведомления → перезапуск → проверка доступа → восстановление backup.
   Если сценарий пересекает проекты, продемонстрировать соответствующие части отдельно.
8. Подготовить короткий разбор: архитектура, 3 инварианта, 3 отказа, результаты измерений,
   ограничения, следующий шаг при росте нагрузки. Защитить решения без подсказок AI.

**Выход:** можешь показать причину проблемы и эффект исправления; понимаешь, что измеренные
результаты относятся к конкретной среде. Не называешь приложение готовым к произвольному highload.

## После обязательного маршрута

Выбирать одно расширение по реальному продукту: SSE/WebSocket, поиск средствами PostgreSQL,
mobile push, полноценная подписка, OIDC-провайдер, offline-sync, Go-сервис, Python-обработка.
Каждое расширение начинается с задачи, ограничений и критерия результата.

Для поиска работы добавить подготовку по выбранным вакансиям: SQL-задачи, объяснение
архитектуры, диагностика инцидента, интервью по runtime и необходимый уровень алгоритмов.
Это отдельный трек; основной план оптимизирован под самостоятельное создание продуктов.
