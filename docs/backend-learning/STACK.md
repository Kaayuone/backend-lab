# Выбор стека и карьерные направления

[К маршруту](README.md). Решение от 2 октября 2026 года: основной язык — TypeScript;
Go и Python изучаются позже при появлении конкретной причины. Это согласованный выбор
пользователя. Библиотеки ниже — рекомендуемые рабочие решения, а не список для установки сразу.

## Почему основной маршрут на TS

Главная цель — свои SaaS и мобильные продукты при бюджете до 10 часов в неделю.
Сильный фронтенд-опыт позволяет направить время на данные, надёжность и эксплуатацию.
Смена языка сейчас добавила бы отдельный учебный слой. Это вывод из целей и исходного опыта,
а не утверждение, что TypeScript объективно лучше остальных языков для любого бэкенда.

Все три варианта позволяют построить рассматриваемые продукты. Они различаются прежде
всего стоимостью входа для этого разработчика и тем, какие дополнительные задачи удобнее решать.

| Вариант               | Что даёт                                                                            | Что дополнительно изучать                                                                     | Когда выбирать                                                                     |
| --------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| TS + Node.js + NestJS | Знакомый язык, общие инструменты с фронтендом, структурированное API                | Node runtime, DI, жизненный цикл приложения, SQL, эксплуатация                                | Основной маршрут для собственных веб- и мобильных продуктов                        |
| Go + net/http + pgx   | Явные серверные компоненты, конкурентность, удобный путь к отдельным сервисам и CLI | Идиомы Go, ошибки, context, goroutines, tooling; продуктовую инфраструктуру тоже надо собрать | Целенаправленный переход в Go-backend или конкретная задача для отдельного сервиса |
| Python + Django/DRF   | ORM, админка и много готовых механизмов для приложений с данными                    | Python, миграции/ORM, модель исполнения, типизация и развёртывание                            | Продукт с важной админкой и предпочтением экосистемы Django                        |
| Python + FastAPI      | API вокруг Python-кода, валидация и OpenAPI                                         | Выбор БД-слоя, миграций, auth, фоновых задач и организация приложения                         | Сервис вокруг обработки данных, ML или Python-библиотек                            |

Возможности фреймворков описаны в [NestJS](https://docs.nestjs.com/),
[Django](https://docs.djangoproject.com/en/5.2/intro/overview/) и
[FastAPI](https://fastapi.tiangolo.com/features/). Для Go полезны
[net/http](https://pkg.go.dev/net/http) и [pgx](https://github.com/jackc/pgx).
Эти ссылки подтверждают механизмы, а вывод о выборе выше — рекомендация для данной ситуации.

## Что можно заключить о рынке

Ориентир — русскоязычный рынок и удалённая работа. На момент проверки 2 октября 2026 года
в выдачах Хабр Карьеры представлены [NestJS](https://career.habr.com/vacancies/skills/nestjs),
[Go](https://career.habr.com/vacancies/skills/golang) и
[Django/Python](https://career.habr.com/vacancies/skills/django), в том числе удалённые позиции.
В примерах встречаются PostgreSQL, Docker, Redis и SQL: знания базы переносятся между языками.

Это иллюстративная проверка живых объявлений, не полный подсчёт вакансий. Страницы по тегам
могут содержать смежные профессии, дубликаты и объявления разных уровней. По их размерам
нельзя честно вывести вероятность трудоустройства или сравнить спрос на языки.
Опросы использования технологий, например
[Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology), тоже не измеряют вакансии.

Практический вывод: сначала расширить существующий профиль до fullstack на TS.
Это сохраняет ценность фронтенд-опыта. Если цель сменится на отдельную backend-карьеру,
сделать новый срез подходящих вакансий и выбрать Go/Python по конкретным требованиям.
Знание синтаксиса нового языка само по себе не переносит senior-грейд из фронтенда в бэкенд.

Перед реальным поиском работы потратить 2–3 часа на 20–30 подходящих объявлений:
записать язык, задачи, требования к SQL/системам, уровень, страну найма, ограничения удалёнки,
английский и форму оформления. Исключить дубликаты и чужие роли. Такой срез полезнее
общего рейтинга языков; он не включён в обязательные часы продуктовой программы.

## Основной набор

| Слой              | Решение                                                             | Зачем и когда появляется                                                      |
| ----------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Runtime           | Поддерживаемая LTS-ветка Node.js, TypeScript strict                 | Один runtime; версию фиксировать в проекте после проверки совместимости       |
| HTTP-приложение   | NestJS с Express-адаптером                                          | Один основной фреймворк; Fastify сравнить позже при необходимости             |
| Архитектура       | Модульный монолит; отдельный worker для долгих задач                | Декомпозиция по ответственности без сети между каждым модулем                 |
| API               | REST/JSON + OpenAPI                                                 | Понятный контракт для web/mobile; runtime-валидация остаётся обязательной     |
| Валидация         | class-validator/class-transformer в Nest                            | Один подход для DTO; не изучать параллельно три schema-библиотеки             |
| БД                | PostgreSQL                                                          | Транзакционные данные, ограничения, запросы, индексы                          |
| Доступ к БД       | SQL → pg в короткой лабораторной → Kysely в приложении              | Сначала понимать запрос; затем получить типизацию без сокрытия SQL            |
| Миграции          | Один runner, например Kysely Migrator                               | Повторяемое изменение схемы; не править применённую миграцию                  |
| Тесты             | Vitest, Supertest, настоящий PostgreSQL для интеграционных тестов   | Проверять контракты и транзакционное поведение                                |
| Конфигурация/логи | Проверка env при старте, структурированные логи через Pino          | Ошибка настройки обнаруживается до приёма трафика; секреты скрываются         |
| Фоновые задачи    | BullMQ + Redis с этапа 6                                            | Повторы, ограничения конкурентности, отдельный worker                         |
| Telegram          | grammY                                                              | Адаптер Bot API; обработчик сообщения не содержит всю бизнес-логику           |
| Медиа             | yt-dlp и FFmpeg как внешние процессы                                | Готовые инструменты скачивания/конвертации; писать Python-сервис не требуется |
| Файлы             | Временный диск worker; S3-совместимое хранилище при изучении файлов | Разделить состояние задачи, метаданные и бинарное содержимое                  |
| Платежи           | Sandbox одного доступного провайдера                                | Начать с checkout/webhook, а не со своего платёжного процессинга              |
| Доставка          | Docker Compose, Linux VPS, Caddy, GitHub Actions                    | Один понятный путь от commit до HTTPS и восстановления                        |

Состав Nest подтверждается [документацией](https://docs.nestjs.com/), типизация SQL —
[Kysely](https://kysely.dev/docs/intro). Совместимость конкретных версий проверять при начале
проекта. Эта таблица не требует обновлять текущие зависимости репозитория.

## Несколько принципиальных решений

**Kysely вместо раннего погружения в ORM.** Сейчас слабое место — написание SQL.
Поэтому полезно видеть запросы и транзакции явно. Prisma/Drizzle/Django ORM можно освоить
позже; переносимая база — SQL, ограничения, план запроса и границы транзакций.

**Express внутри Nest.** Это достаточный учебный вариант. Смена HTTP-адаптера не исправляет
медленный SQL, неограниченный параллелизм или блокировку event loop. Fastify остаётся
доступной альтернативой без обязательного второго переписывания приложения.

**Монолит и worker.** API и фоновые задачи могут использовать один репозиторий и общие
модули, но запускаться отдельными процессами. Это уже позволяет отделить длительную
обработку от HTTP без введения набора микросервисов.

**Redis по потребности.** В начале данные и сессии могут жить в PostgreSQL. Redis появляется
из-за очереди. Кэш добавляется только после измерения и с описанной политикой устаревания;
очередь и вытесняемый кэш требуют разных настроек сохранности/eviction.

**Auth.** В учебной работе один раз разобраться с серверной сессией и её отзывом.
Для реального продукта сравнить готовую auth-библиотеку/провайдера с собственной поддержкой.
JWT не является обязательным условием REST или мобильного API. Для внешнего входа изучить
OIDC Authorization Code + PKCE; собственный сервер выдачи OAuth-токенов не строить.

## Когда добавлять Go или Python

Go имеет смысл после базы, если целевые вакансии требуют его или появился отдельный
серверный компонент с понятными требованиями. Проверка гипотезы: за 20–30 часов написать
небольшой сервис на `net/http` + `pgx`, освоить context/cancellation, ошибки и тестирование.
Это знакомство, не готовность к Go-вакансии; оставшиеся пробелы оценивать отдельно.

Python имеет смысл, если продукт зависит от Python-пакетов, обработки данных или нужен
Django. Пробный объём 15–25 часов: одно прикладное преобразование данных и API к нему,
типизация, тесты, окружение и контейнер. Вызов LLM по HTTP сам по себе не требует Python.

Для бота наличие Python внутри yt-dlp не означает необходимость изучить новый основной стек.
Если инструмент запускается отдельным процессом, приложение взаимодействует с его
аргументами, кодом завершения и файлами. Установку нужного runtime включить в образ worker.
