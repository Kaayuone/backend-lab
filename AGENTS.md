# Правила работы в backend-lab

Правила действуют для всего репозитория. Явные указания пользователя для текущей задачи
имеют приоритет. Общие навыки и шаблоны работы нужно применять с учётом этих правил.

## Назначение и структура

Это учебный репозиторий для освоения бэкенда и создания собственных SaaS и мобильных продуктов.
Пользователь — опытный frontend-разработчик; новые серверные механизмы нужно объяснять
на конкретных сценариях, с причинами решений и проверкой поведения при сбоях.

- `old/garage-rest-api/` — архивная практика на NestJS, TypeScript, PostgreSQL и Kysely.
- `old/garage-database/` — архивные упражнения на Fastify и PostgreSQL.
- `old/` — прежние проекты и их инфраструктура; новые проекты создавать вне архива.
- `docs/backend-learning/` — актуальный план: границы, стек, этапы, проекты и прогресс.
- `docs/BACKEND_LEARNING_PLAN_v2.md` и `docs/plan/` — устаревшие планы, сохранённые как история.
- `old/docker-compose.yml` — инфраструктура архивных проектов. Порты и состояние контейнеров проверять
  по текущим файлам и окружению, а не по старому плану.

Основной учебный стек — TypeScript, Node.js, NestJS, PostgreSQL и Kysely.
Go/Python и дополнительные сервисы добавляются по конкретной задаче.
Будущие проекты из плана не считать уже реализованными.

## Границы задачи и учебная работа

- Перед изменением проверить код, применимые инструкции и Git-состояние.
  Сохранять существующие пользовательские и несвязанные изменения.
- При запросе объяснения, ревью или команды сначала дать объяснение, выводы или команду.
  Такие запросы сами по себе не разрешают менять код, зависимости, инфраструктуру и данные.
- Выполнять уже разрешённую работу без повторных запросов подтверждения.
  Если ответ пользователя действительно нужен, объяснить конкретную причину.
- Не расширять узкий запрос: установка зависимости не означает внедрение новой архитектуры,
  изменение документации не означает реализацию описанных проектов.
- Использовать фактические файлы и текущую схему для примеров. Давать команды для PowerShell;
  при объяснении SQL сначала показать сам запрос и его эффект.
- Новые SQL-запросы, транзакции, правила доступа и обработку событий сопровождать объяснением
  инвариантов и важных отказов. Избегать повторного создания уже понятного каркаса.
- Не отмечать учебный этап выполненным только по наличию кода. Прогресс менять по подтверждённым
  результатам; старые планы сохранять с отметкой об устаревании.

## Git: коммитим в main

- **В этом репозитории коммиты делаем непосредственно в `main`.**
  Отдельную ветку создавать только по явному запросу пользователя.
  Если навык по умолчанию предлагает новую ветку, применять этот workflow в `main`.
- Перед коммитом проверить текущую ветку. Если открыта другая ветка, проверить историю
  и возможность сохранить рабочие изменения перед переходом в `main`.
- Создавать коммиты по запросу пользователя; запрос сообщения коммита разрешает только
  подготовку сообщения. Push выполнять только по отдельному явному указанию.
- Добавлять в index явные пути или выбранные hunks. Не использовать `git add .` или `git add -A`,
  если они могут захватить несвязанные изменения.
- При смешанных правках одного файла включать только относящиеся к задаче hunks,
  сохраняя остальные в рабочем дереве. Не изменять рабочие файлы ради разделения коммитов.
- Делить независимые цели на логические коммиты; код, относящиеся тесты и документацию
  одной цели сохранять вместе.
- Перед каждым коммитом использовать `generate-commit-message`: Conventional Commits,
  краткий английский subject и содержательный body, без AI-атрибуции.
- Проверять staged-состав, полный staged diff и `git diff --cached --check`.
  После коммита проверять его состав и оставшееся рабочее дерево.
- Не включать `node_modules`, сборочные артефакты, `.env` и секреты.
  Не обходить hooks и не применять разрушительные Git-команды.

Корень Git — `backend-lab`, приложения вложены в него. При ошибке dubious ownership использовать
`git -c safe.directory=D:/Work/backend-lab ...`, не меняя глобальную конфигурацию автоматически.

## Код и данные

- Следовать текущим соглашениям приложения: TypeScript strict, ESM и `.js` в относительных
  импортах Nest-кода. Не вводить второй основной подход без причины.
- Разделять HTTP-вход, бизнес-операции и доступ к БД. Ограничения данных защищать
  схемой и транзакциями, а не только предварительными проверками в приложении.
- Nest-интерфейсы не являются runtime DI-токенами. Для абстракций использовать явные токены
  и обновлять соответствующие mock providers в тестах.
- PostgreSQL BIGINT ID сохранять строками на границе JS. Для NUMERIC и денег учитывать
  точность и валюту; не преобразовывать произвольные большие ID через `Number` или `+id`.
- Изменение схемы оформлять новой миграцией и согласовывать типы, seed и тестовые fixtures.
  Применённые миграции не переписывать.
- Запуск миграций, seed, изменение живых данных и пересоздание volumes выполнять только
  в рамках разрешённой задачи. Перед изменением данных проверить схему и затрагиваемые записи.
  Для объяснения ручной работы с БД предпочтительны шаги в pgAdmin с предварительным показом SQL.
- Dev seed и тестовые fixtures держать отдельно. Не использовать реальные личные данные в тестах.
- Сохранять комментарии о нетривиальной логике и ограничениях; не добавлять пересказ кода,
  историю обсуждения или закомментированные реализации.

## Проверки

Команды выполнять из соответствующего приложения, а не из корня по предположению.

Для архивного `old/garage-rest-api/`:

```powershell
npm run build
npm run lint
npm test
```

Для изменений HTTP/БД при подготовленной изолированной тестовой среде:

```powershell
npm run test:e2e
```

E2E требует явного `TEST_DATABASE_URL` с базой `garage_test`. Не использовать fallback
на `DATABASE_URL`. Setup применяет миграции, тестовая очистка удаляет данные; сначала
проверять адрес и защиту тестовой БД. Создание/закрытие соединений и setup/teardown ожидать через `await`.

Для архивного `old/garage-database/` использовать его scripts: `npm run build:ts` и `npm test`.
Для новых проектов брать команды из их собственных `package.json`.
Объём проверок выбирать по изменению. Для документации достаточно форматирования, проверки
ссылок и `git diff --check`; запускать весь набор тестов приложения не требуется.

Тестами защищать наблюдаемое поведение и важные контракты: права доступа, транзакции,
пограничные данные, повторы и отказы. Не добавлять тесты только ради покрытия строк.
В итоговом ответе указывать только реально выполненные проверки и их результат;
проверку сборки не выдавать за проверку миграции на БД.
